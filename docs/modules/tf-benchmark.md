# tf-benchmark —— 压测模块

> **状态**：✅ **已实现**（2026-10-29，[changelog 0075](../changelog/0075-tf-benchmark五场景压测器.md)）。
> 12 个主源文件 + 3 个测试类（21 用例），零第三方运行时依赖（仅 JDK `HttpClient`）。
> **不入服务拓扑**：按需 `java -cp` 运行，不随服务发布。
>
> 实跑产出的报告归档在 [`docs/benchmark/`](../benchmark/README.md)。
> §5 保留了 2026-10-27「M6 撤下承诺」的原始决策及其被推翻的过程——**先看历史再看结论，
> 才知道当初为什么不敢做、后来凭什么敢做**。

## 1. 它解决什么问题

在此之前压测靠 `wrk` / `ab` 这类通用工具，有两个绕不过去的坑：

| 坑 | 后果 | 本项目怎么解 |
|---|---|---|
| **鉴权** | 多数接口要 JWT，`wrk` 得手写登录脚本；不带 token 全是 401 | 内置登录换 token（`--phone/--password`），自动带上 |
| **业务码** | 本项目**鉴权失败也是 HTTP 200 + `code=40101`**，只看状态码会压出假 QPS 和 100% 成功率 | 成功 = `2xx && businessCode == 0`，错误码单独计数 |
| **不可复现** | 每次参数靠手敲、结果靠肉眼看终端 | 参数全部具名，报告落 Markdown 文件（含机器/时长/分位口径快照） |
| **写场景造数** | 点赞/评论要有真实 `mediaId`，否则全是 404 | `--post-ids` 显式给内容身份池，随机环绕取样 |

**它不是什么**：不是压测平台、不做分布式加压、不做流量录制回放。定位是「**一条命令产出一份可归档、可对比的报告**」。

## 2. 五个场景

| `--scenario` | 方法与端点 | 需要鉴权 | 需要内容池 |
|---|---|---|---|
| `feed`（默认） | `GET /api/v1/feed/recommended?page&size` | 否 | 否 |
| `playable` | `GET /api/v1/feed/playable?postIds` | 否 | ✅ |
| `comment-list` | `GET /api/v1/comments?mediaId&size&mode` | 否 | ✅ |
| `like` | `POST /api/v1/feed/media/like` | ✅ | ✅ |
| `comment-publish` | `POST /api/v1/comments?mediaId&content` | ✅ | ✅ |

## 3. 怎么跑

```bash
# 只读场景
java -cp "tf-benchmark/target/classes:<deps>" com.turbofeed.benchmark.BenchmarkMain \
  --base-url http://127.0.0.1:8080 --scenario feed \
  --concurrency 24 --duration 15s --warmup 3s --target-rps 2000

# 写场景：必须先给真实内容身份
java ... --scenario like --post-ids <id1>,<id2> --phone 13800138000 --password 123456
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--base-url` | 必填 | 被测服务地址 |
| `--concurrency` | 8 | **闭合环路**：N 线程「发一条 → 收到再发」= N 个并发用户 |
| `--duration` | 30s | 正式计时窗口（不含预热） |
| `--warmup` | 5s | 预热窗口，样本**丢弃**；预热期成功率 <50% 直接中止（配置问题） |
| `--target-rps` | 0（不限） | QPS **上限近似**，靠 `parkNanos` 节流，不是真 open-loop |
| `--post-ids` | — | 逗号分隔内容身份池 |
| `--output` | `target/benchmark/` | 报告落盘目录 |

**退出码**（给 CI 当性能门禁用）：`0` 成功率 ≥99% / `1` 跑完但低于红线 / `2` 参数或登录失败（无有效数据）/ `3` 报告写入失败。

## 4. 报告与判读口径

- **分位用最近秩（nearest-rank）**，`ceil(p*n)-1` 取下标，**不插值**——插值出来的 p99 不是任何一次真实请求的延迟。
- **自动判读三条红线**：成功率 ≥99%、p99 ≤500ms、无鉴权类错误（`CODE:401*`）。三条全过才 ✅。
- 命中红线内但**仍有失败请求**时给 🟡——99.37% 也是达标，但那 174 条失败不该被一个 ✅ 盖住。

## 5. 历史：M6 曾决定「撤下承诺」（2026-10-27 → 2026-10-29 推翻）

**2026-10-27 的决策**：不实现，删掉 README 里「自带压测模块」的承诺。理由是三个前提一个都不满足——
没有容量目标、没有可复现数据基线、没有「压测结论 → 容量决策」的闭环。
结论原话：**错误的数字比没有数字更危险**。

**2026-10-29 为什么又做了**：那三个前提不是「压测模块的前置条件」，而是**用压测模块才能造出来的东西**。
把因果倒过来看，就该先有一个能把参数固定住、把口径写进报告的工具，才谈得上基线与目标。
于是 #307 补齐实现，但**不宣称容量结论**——报告归档在 `docs/benchmark/`，每份都写明环境与边界。

## 6. 已知边界（别拿单机数字当生产容量）

1. **单机同进程竞争**：压测器与业务服务跑同一台机器时，数字是「零网络成本下的处理能力上界」，不是生产容量。
2. **闭合环路 ≠ open-loop**：并发数是用户数，`--target-rps` 只是节流上限；被测服务变慢时会自动降速，不产生真实排队。
3. **无分布式加压**：单进程受 GC、CPU、网卡限制，压不满多实例集群。
4. **写场景会产生真实数据**：`like` / `comment-publish` 会真的写库，重复压会产生脏数据与重复点赞。
