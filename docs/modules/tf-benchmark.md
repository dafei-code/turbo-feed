## 1. 为什么保留这个空模块

不是「忘了删」，是刻意留位：

- 目录结构（`runner` / `generator` / `scenario` / `report`）已经表达了**规划中的分层**，
  删掉再建等于把设计意图丢掉；
- 保留在 reactor 里可以让 `mvn` 每次构建都提醒「这里还有一件没做的事」；
- README 与本文档都显式标注未实现，避免读者把规划当现状。

**但这条理由有时效**：M6 必须给出结论——要么实现，要么从 README 撤下承诺并删除模块。
长期保留一个空模块本身就是技术债。

## 3. 现在怎么压测

模块空着，不代表不能压测——直接用外部工具，**结果同样可复现**：

```bash
# Feed 读取
wrk -t8 -c200 -d60s --latency "http://localhost:8080/api/feed/recommended?page=0&size=10"

# 需要登录态的场景先用 curl 拿 JWT，再带 Authorization 头
wrk -t8 -c200 -d60s -H "Authorization: Bearer <jwt>" "http://localhost:8080/api/feed/recommended"
```

> 压测前请先确认真实容量目标。**没有目标的压测只会产出一个数字，不会产出决策**。

## 4. 兑现条件（若将来要做）

要做成「自带压测模块」，至少需要：

1. 明确的容量目标（QPS / P99 / 数据量），否则报告无法判断合格与否；
2. 一个**可重复**的数据基线（造数脚本 + 固定随机种子），否则两次压测不可比；
3. 结论能落到容量规划上（需要几台、瓶颈在哪一层）。

三者缺一，都会让这个模块沦为「跑一次出个漂亮数字」的摆设。

## 5. M6 结论：撤下承诺，保留占位（2026-10-27）

**决定**：不实现。删除 README 里「自带压测模块与可复现性能报告」这句承诺。

**为什么选「撤下」而不是「硬做出来」**：§4 的三个条件目前**一个都不满足**——
没有承诺过的容量目标、没有可复现的数据基线、也没有一份「压测结论 → 容量决策」的闭环。
在这种状态下写一个压测器，产出的只会是一组没有参照系的数字；而数字一旦进了 README，
下一个人会拿它当基准做决策。**错误的数字比没有数字更危险**，所以宁可不做。

**为什么保留空模块而不删**：

- 四个包名（`runner` / `generator` / `scenario` / `report`）记录了当初的分层意图，
  删掉之后重新设计还要再想一遍；
- 保留在 reactor 里，每次构建都提一次「这里还有一件没做完的事」；
- 它与「宣称已实现」的差别是**是否明说**——现在 README、本文档、模块树三处都标了未实现，
  不存在误导风险。

**删除条件（写死，避免占位变成永久技术债）**：出现下列任一情况即删除本模块与对应文档，
并把 README 模块树同步去掉：

2. 一年内仍无容量目标——说明「自带压测」不是这个项目的真实需求，占位没有意义；
