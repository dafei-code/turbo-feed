# 0061 兴趣画像时间衰减 —— 权重从"终身累计和"变成"按半衰期衰减的当前值"

- 日期：2026-09-29
- 影响模块：`tf-feed-engine`（`InterestService`）
- 类型：行为修正；新增配置 `turbofeed.feed.interest.half-life-days`（默认 14）与 `min-score`（默认 0.01）
- 验证：`InterestDecayVerify` 19/19；**老版本对照 0 PASS / 3 FAIL → 改造后 3 PASS**；全套回归 102 PASS / 0 FAIL

---

## 一、为什么要做这个

改造前画像就是一张**只增不减的累计表**：

```java
redisTemplate.opsForHash().increment(key, tag, weight);
redisTemplate.expire(key, TTL);   // 唯一的"衰减"：整份 30 天过期
```

三个致命后果：

| # | 后果 | 具体表现 |
|---|---|---|
| 1 | **兴趣不可迁移** | 用户三年前刷搞笑、现在只看健身，"搞笑"的累计分永远压过"健身"——画像表达的是**历史总量**而不是**现在的偏好** |
| 2 | **悬崖式失效** | 只靠整份 TTL，29 天和 31 天的差别是 100% → 0%，中间没有任何过渡 |
| 3 | **噪声被固化** | 早期大量随机行为的累计分会长期锁住召回位，新行为永远追不上 |

抖音的解法是**长期兴趣（慢衰减，半衰期以周/月计）与短期兴趣（快衰减，以小时/天计）分层**。
本期先落**单画像 + 可配半衰期**，因为它是分层的前提：没有衰减，短期层也无法从长期画像里分离出来。
**双层画像列为下一步（未做）。**

## 二、实现

### 数学模型：全局衰减 == 逐事件衰减

按半衰期 `H` 的指数衰减定义为：每个历史贡献 `w_j` 在时刻 `t` 的价值是 `w_j · 0.5^((t - t_j)/H)`。

朴素实现要给每个事件存时间戳。但注意到：
**同一半衰期下，所有历史贡献在任意时刻经历的衰减量是相同的**——
所以在每次写入时把**旧总量整体乘一个因子** `0.5^((now - lastTs)/H)`，结果完全等价于逐事件衰减。
于是只需要**一个时间戳**，不需要 per-tag、更不需要 per-event 存储。

### 为什么是「单 key Hash + 哨兵字段」而不是「ZSET + 独立 ts key」

最初设计是 `tf:user:interest:{userId}` ZSET + 一个 ts key，用 Lua 一起改。但 Redis **集群**
有个硬约束：**Lua 脚本里的多个 KEY 必须落在同一个 slot**，否则 `CROSSSLOT`。
要保证这点，键名必须写成 hash tag（`tf:user:interest:{123}`）——**这会改变已有键名**，
导致所有现存画像瞬间失联，而所有验证脚本的清理语句也全指向旧键名。

改成本方案后，Lua 只碰**一个** KEY，天然同 slot，**键名一个字都不用改**：

```
tf:user:interest:<userId>   Hash
   ├─ <tag> → 衰减后的累计权重
   └─ __ts__ → 上次写入的 epoch 毫秒（哨兵字段）
```

代价：读路径要跳过哨兵字段。约定 **以 `__` 开头且结尾的字段都不是兴趣标签**。

### 为什么必须是 Lua

衰减是「读出全部 → 逐个乘因子写回 → 再加本次权重」的**读改写（RMW）**。
放在 Java 里做，同一用户的并发行为事件会互相覆盖丢权重——而前端是
**2 秒批量上报**（一次请求几十条事件），这个并发是真实存在的。
Lua 在 Redis 内单线程执行，天然原子。

```lua
local raw = redis.call('HGET', key, tsField)      -- 1. 取上次时间戳
if last and now > last and halfLife > 0 then
  factor = math.pow(0.5, (now - last) / halfLife) -- 2. 算衰减因子
end
if factor < 1.0 then                              -- 3. 整体乘因子（低于阈值则删除）
  local all = redis.call('HGETALL', key)
  for i = 1, #all, 2 do ... end
end
for i = 7, #ARGV do                               -- 4. 加本次权重
  redis.call('HINCRBYFLOAT', key, ARGV[i], delta)
end
redis.call('HSET', key, tsField, tostring(now))   -- 5. 更新时间戳 + TTL
```

返回值 `HLEN` 便于观测画像规模。

### 读路径：同样衰减，但**不回写**

`weightedTags` 读到的那一桶 `HGETALL` 里已经包含 `__ts__`，**零额外成本**就能算出当前值。
不回写纯粹是成本考虑：读请求远多于写请求，为省这点计算去多一次 Redis 写不划算。

⚠️ 代价：`0.5^(elapsed/halfLife)` 这个公式在 Lua 与 Java（`decayFactor`）里各有一份，**改一处必须改另一处**。
代码里已双向标注。这是"不引入 Lua 之外的共享机制"换来的取舍，不是遗漏。

### 遗忘阈值 `min-score`

指数衰减只会趋近 0 不会到 0。不清掉的话，画像里会永久躺着一批 `1e-9` 级的长尾标签：
占内存，还污染 TopN 的比较。

取 **0.01**（连一次不完整观看 0.1 的十分之一都不到）→ 语义上等于"已经不在乎了"，直接 `HDEL`。

### 负权重也参与衰减

`DISLIKE = -1.5` 会被一并乘因子（`-1.5 → -0.75`）。
这是刻意的：**负反馈同样应该有时效**——半年前点过踩，不代表今天还讨厌。
`math.abs(decayed) < minScore` 保证负向弱信号也被清理。

### `hasInterest` 的判据改成 `size > 1`

加了哨兵字段后 `HLEN` 至少是 1。只剩哨兵 = 所有标签都已被遗忘 = 没有画像。
刻意保留 O(1) 的 `HLEN` 而不是改成复用 `weightedTags`——它是 `readPage`
每次都走的前置闸门，若内部再调一次 `weightedTags`，一次读请求就把画像扫两遍。

## 三、配置

```yaml
turbofeed.feed.interest:
  half-life-days: 14   # 半衰期：14 天前的同量权重只剩一半
  min-score: 0.01      # 衰减到该绝对值以下 = 遗忘，标签移出画像
```

`half-life-days <= 0` 表示**关闭衰减**（行为退化为改造前），便于灰度与回滚。

不靠 sleep（14 天没法等）——直接把 `__ts__` 往前拨。衰减唯一依赖的就是它与当前时间的差，
这让测试秒级可跑，也让"过了几个半衰期"成为精确可控的输入。

## 五、已知取舍与未完成项

- **未做：长期/短期双层画像**。抖音的做法是长期画像（慢衰减）+ 短期画像（快衰减，用于捕捉最近 burst），
  两者分别参与召回。本期只有单层——Snapshot mode 的半衰期是"长期"量级，短期的突发兴趣
  （连着刷 20 条钓鱼视频）在单层模型里仍会被历史均值稀释。这是下一步最该补的一块。
- **存在 Redis 里的旧画像没有 `__ts__` 字段**：读时按"时间未知"处理（`factor = 1.0`，不衰减），
  第一次有新行为时就会被写路径带上正常的 `__ts__`，从此进入正常的衰减轨道。
  这是一次性过渡态，不是持续错误。
- **线上灰度**：先把 `half-life-days` 调到很大（如 365）观察，确认画像 TopN 稳定后再调到目标值。
  直接切到 14 天会让长期活跃用户的画像在第一次写入时集体"缩水"（这是预期行为，但影响面需要评估）。
