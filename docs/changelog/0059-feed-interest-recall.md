# 0059 兴趣召回接线 —— 多路召回的第三路（画像从"只加权"变成"能召回"）

- 日期：2026-09-29
- 影响模块：`tf-feed-engine`（`InterestService` / `FeedTimelineStore`）
- 类型：新增能力；新增配置 `turbofeed.feed.interest-recall-ratio`（默认 0.15）

---

## 一、为什么要做这个（对齐抖音多路召回）

抖音的召回是**多路并行**的：协同过滤 / 双塔向量 / 兴趣标签 / 关注社交 / 同城 / 热门 / 冷启动保量，
每路各取几千条再合并去重。**"按兴趣专门去找内容"是其中独立的一路**。

改造前我们只有两路：

| 路 | 语义 |
|---|---|
| 流量池时间线 | 按入流时刻切片，池权重分配槽位 |
| 热点榜（0053） | 全站热度 TopN，人人相似（探索位） |

而用户画像**只用于给已召回的内容加权**——候选来自流量池，画像只能在这些"已经捞上来的东西"
里调顺序。这有个直接后果：**用户永远看不到池外的同类好内容**。
"因为你有这个兴趣，所以专门去找这类内容"这条通路是不存在的。

更讽刺的是：`TagIndexService#mediaWithTag`（标签 → 内容索引）**早已建好、零调用**——
索引有了，读路径没接。

## 二、实现

### 召回逻辑放在 `InterestService`（不是 `FeedTimelineStore`）

新增 `InterestService#recallTimelineKeys(userId, limit)`：画像 Top10 正向标签
→ 逐个 `mediaWithTag(tag)` → **多标签轮转（round-robin）**取候选。

**为什么轮转而不是按权重依次填满**：若按权重从高到低取满，权重最高的一个标签会吃光所有槽位，
结果就是"你点过一次美食，整页全是美食"——这正是信息茧房的成因。
轮转保证多个兴趣标签各有代表。召回层管**覆盖**，重排层的"同类不连刷"管**相邻不重复**，两者互补。

### 负反馈在召回阶段就生效（不只是排序扣分）

`srecallTimelineKeys` 会先取负向标签集，**跳过用户点过"不感兴趣"的标签**。

只在排序阶段扣分是不够的：**只要它还在候选里，就总有机会被排上来**；
而"别再给我推这类"的语义是**根本不要进候选**。

### 读路径接线（`FeedTimelineStore#readPage`）

单页槽位切成三段，均从 `limit` 里扣，剩余才归流量池：

```
热点位（探索，人人相似） → 兴趣位（个性化，因人而异） → 流量池（通用排序）
```

- **只排除热点位，不排除流量池候选**——刻意的。若把流量池全部候选都排除，
  召回就只剩"3 天合并窗口之外"的老内容可捞；而召回真正想捞的恰恰是
  **"在池里但排不进当前页"**的同类好内容（池是按入流时刻切片的，深页内容永远翻不到）。
- 重复问题交给流量池解析时按 `interestKeys` 去重：谁先占位谁算，最终单页不出现重复条目。
- 兴趣位内部仍按 `RankingModel` 精排分排序：召回只保证"这类内容进得来"，
  不保证"质量差的也往前放"。
- 兴趣位**不参与**后续"同类不连刷"打散：召回层已按多标签轮转保证覆盖，
  再交给打散层重排会抹掉"兴趣优先"的语义。

### 时间序取值

时间线 ZSET 的 score 是"入流时刻"，但兴趣召回的内容来自标签索引，不必然落在当前合并窗口内，
拿不到它的入流 score → 用**内容创建时间**作同量纲（epoch 毫秒）代理（标签索引 7 天 TTL，二者相差有限）。

## 三、验证

`target/verify/InterestRecallVerify.java`（真 Redis 集群 + 真实 Store/InterestService）**9/9 PASS**。

场景：把用户感兴趣的内容**刻意放在池底**（最早入流），中间插 6 条更新的无关内容。

| # | 断言 | 结果 |
|---|---|---|
| ③ | 关闭召回：java 内容不在前 2 位（证明它本来翻不到） | PASS |
| ④ | 开启召回：java1 进前 2 位（个性化槽位生效） | PASS |
| ④b | java2 也进前 2 位（第二个槽位） | PASS |
| ④c | 单页不超过 `limit` | PASS |
| ④d | 单页无重复条目 | PASS |
| ⑤ | 无画像用户不产生兴趣位（冷启动不召回） | PASS |
| ⑥ | 负反馈后 java 不再占据个性化槽位 | PASS |

页内顺序实测：

```
关闭召回: [ir_cook6, ir_cook5, ir_cook4, ...]
开启召回: [ir_java1, ir_java2, ir_cook6, ir_cook5, ...]   ← 池底内容被捞到前两位
负反馈后: [ir_cook6, ir_cook5, ir_cook4, ...]             ← 召回阶段就排除
```

## 四、踩坑记录

- **改完必须重新编译再跑 harness**：`run_*.sh` 只 javac 测试文件，
  引擎主代码靠 `mvn compile`。有一次改了负反馈过滤却没重编，跑出来的结果仍是旧行为，
  误判为"过滤没生效"。
- **e2e 遗留数据会污染召回测试**：端到端上传的那条 caption 含 `#java`，
  会和测试内容争抢召回槽位。验证脚本一律用**测试专属标签**（`irjava` / `ircooking`）。
