# 0067 抖音式「流量池分级 → 加严复审」闭环（Tier3：越火审得越严）

> 状态：已落地 · 已真实启动验证（网关 8080 + 引擎 8083）· 已端到端验证（tier3_verify.sh 全绿 18/18）
> 关联：抖音分层审核模型（机审初筛 + 账号信用分级 + 举报/申诉闭环 + 热度复审）；
> Tier1（0065 举报累计复审队列）；Tier2（0066 热度阈值复审队列）；feed-engine 流量池晋级器；RBAC（CONTENT_TAKEDOWN）；penalty 体系

## 一、为什么需要（补「晋级不加严」缺口）

抖音的内容安全是**分层 + 循环持续审核**，流量池既是分发旋钮也是风控闸门：内容在小池验证 → 互动率达标晋级 →
**每上一个台阶，审查力度同步加码**（不是"上了热门就一路狂奔"）。Tier1（0065）补了「举报累计触发复审」，
Tier2（0066）补了「热度超限触发复审」，但两者都还缺一个关键维度：

> feed-engine 的流量池晋级体系（L1 小池 → L2 → L3 大池，按互动率赛马晋级）**已经存在**，
> 但内容**晋级到更高池时，没有触发任何额外审核**——而更高池意味着**远大于小池的公域曝光**。
> 同时 Tier2 的热度阈值是**全局固定 1000**，不随池收紧：
> 一条已在 L3 大池拿到海量曝光的内容，要走完同样多的互动才肯再审一次，"越火审得越严"是缺一半的。

本变更落地三档补强方案的**第 3 档（流量池分级）**：

> 当内容**晋级到更高流量池**时，feed-engine 回调网关，网关执行**三件套加严**：
> ① 机审复扫（fail-closed：命中即整帖下架 + 扣分 + 处罚）；
> ② 建一条 `POOL_PROMOTED` 复审任务交 `REVIEWER` 人工复核（**晋级必过人审**）；
> ③ 把该帖的热度复审阈值**按池级收紧**（L1=1000 / L2=500 / L3=200），
> 使更高池**更快**触发 Tier2 的 `HEAT_ACCUMULATED` 复审。

**与 Tier1/Tier2 的关系**：共用同一条 `review_task` 队列、`ReviewTaskRepository` 与 `decideReviewTask`
处置流程，仅 `taskType` 不同（`POOL_PROMOTED`），CD 复用、不双计；第 ③ 条正是把 Tier2 的
热度阈值从"全局常量"升级为"随池收紧"，两档共同完成抖音式「越火审得越严」。

## 二、设计

- **触发点（跨服务）**：`FeedPoolPromoter#scanNow` 在 `FeedTimelineStore#promote(timelineKey, target)`
  **成功之后**回调网关 `POST /internal/review/pool-promoted?postId=&from=&to=`。
  放在"已成功晋级"之后很关键：**晋级本身是发布侧信号，加严是旁路治理**，不能因加严失败回滚晋级。
- **回调客户端（新增，fail-open）**：`GatewayReviewClient`（RestClient，base-url 与超时外置），
  任何失败（不可达/超时/非 2xx）仅 WARN 返回 false，**绝不阻断晋级扫描主流程**。
  超时显式配置（connect 500ms / read 2s），避免网关故障时扫描线程被慢调用拖垮。
- **网关侧入口**：新增 `InternalReviewController`（`@RequestMapping("/internal/review")`）。
  路径在 `/internal/**` 下，`WebConfig` 只对 `/api/admin/**` 注册 `PermissionInterceptor`，
  故不受 RBAC 拦截，依赖网络边界（Ingress 拒绝外部访问）——与引擎 `/internal/feed/**` 同源约定。
- **三件套（`MediaReviewService#onPoolPromoted(postId, from, to)`）**：
  1. **机审复扫**：对代表图重跑 `ContentModerationRouter#moderate(mediaId, userId, url)`；
     命中 `REJECTED` → `takeDownAndPenalize(...)`（`ViolationSeverity.HIGH`，来源
     `ViolationSource.POOL_PROMOTED`），并**不再建人审任务**（避免同内容重复处置）。
  2. **建 `POOL_PROMOTED` 复审任务**：仅当内容仍 `APPROVED` 且**无未决任务**时建单；
     `triggerCount` 填本次晋级到的池级（2 或 3），便于复盘"它是在哪一级被拉下来的"。
  3. **收紧该帖热度阈值**：写 Redis 覆盖键 `tf:media:heat-threshold:{postId} = poolHeatThreshold(to)`；
     Tier2 的 `onInteraction` 优先读该覆盖值，读不到才回落全局默认。
- **为什么每帖至多一条待处置 POOL 任务（去重）**：与举报/热度同构，走 `existsOpenForMedia` 去重。
  连续晋级（L1→L2→L3 可能只隔数秒）若每级都开单会把审核台刷爆；更重要的是
  **内容已在人工复核中，重复开单没有增量价值**。因此：阈值覆盖值每次晋级都刷新（始终反映当前池级），
  而任务在旧任务处置前不重复创建——这是刻意取舍，不是遗漏。
- **阈值外部化**：`MediaProperties.Review` 新增 `poolHeatThresholdL1=1000 / L2=500 / L3=200`
  （键 `turbofeed.media.review.pool-heat-threshold-l1/2/3`），调参不发版。
  `poolHeatThreshold(pool)` 用 `switch` 取对应池级，`default` 兜底回全局 `heatReReviewThreshold`。
- **存储取舍**：阈值覆盖值是**每帖实时信号**，存 Redis（与 Tier2 热度计数同键型、`postId` 同维度），
  不落库不引新存储；任务本身仍落 `review_task` 单表（DB 为权威）。**无新增 DDL**。

## 四、验证证据（真实启动 + 端到端，18/18 全绿）

- 真实启动：网关（8080）与引擎（8083）双双 `Started ...Application`，
  双模块 `mvn compile` 通过，**日志 0 异常**；引擎侧确认
  `网关回调客户端初始化: baseUrl=http://localhost:8080, connectTimeoutMs=500, readTimeoutMs=2000`。
- 端到端脚本 `target/verify/tier3_verify.sh`（真实 HTTP，全绿 18/18）：
  1. 管理员登录拿 token ✅
  2. 注册作者 → 上传 → 审核 `APPROVED` → **显式等到 `currentPool==1`**（拒绝"发布→进池"竞态）✅
  3. 上报行为（30 曝光 + 10 点赞，互动率≈0.33）并转发到引擎 ✅
  4. **L1→L2 晋级**：自动建 `POOL_PROMOTED` 任务，`triggerCount=2`，
     Redis 覆盖键 `tf:media:heat-threshold:{postId}` = **500**（覆盖全局 1000）✅
  5. **L2→L3 晋级**：重建一条新的 `POOL_PROMOTED` 任务（旧任务已维持发布处置），
     覆盖键收紧为 **200** ✅
  6. **证明覆盖值被真正消费**：内容已在顶池（阈值稳定 200），重置热度计数后
     **只报 200 个赞就触发 `HEAT_ACCUMULATED`**（若仍按全局 1000 判断，200 赞绝不会触发）✅
  7. 第二帖：晋级建 `POOL_PROMOTED` → REVIEWER `decide(takedown=true)` → 任务翻 `status=2`（整帖下架）✅

## 五、环境注意（踩过的坑，避免复发）

- **两个偶发失败都不是功能缺陷，务必先按此排查**：
  1. **"发布→进池"是事务提交后的下一跳**。若内容还没落进任何池（`currentPool=0`）就触发晋级扫描，
     晋级器会把它**直接从待评估集合移除**，本轮不会晋级 → 表现为"回调没发生/任务没建"。
     脚本里已显式等待 `currentPool==1` 再扫描，把这个竞态变成确定性前提。
  2. **引擎有 30s 周期的后台晋级调度器**，会在脚本执行期间**自行**把 L2 推到 L3 并改写覆盖阈值，
     使"按 500 触发 HEAT"的断言失效（计数 500 ≠ 已被改写成的 200）。
     因此阈值读取的验证必须放在**内容已到顶池 L3、阈值稳定**之后再做（L3 是 `MAX_POOL_LEVELS`，无法再晋级）。
- **本机 Redis 集群**：宿主曾出现约 7.5 分钟停顿（`Thread starvation or clock leap detected`），
  导致连接池留下 stale 连接、后续命令报 `Redis exception`（确认集群与三个主节点本身健康：
  `cluster_state:ok`、slot 全覆盖、`AUTH+PING` 全通）。**处置：重启网关与引擎刷新连接**，即用 `run_in_background`
  拉起，避免 `nohup ... &` 被回收。
- **`dependency:build-classpath` 的 `-Dmdep.outputFile` 相对路径是相对模块目录的**，
  而 run 脚本读的是仓库根 `target/verify/cp-*.txt`（曾写成空文件导致 classpath 缺 m2 依赖、应用起不来）。
  用**绝对路径**输出即可。
- **bash `$VAR` 紧邻全角标点会被当成变量名的一部分**（`$POOLID，` → 报 `POOLID?: unbound variable`），
  脚本里所有变量统一用 `${VAR}` 形式。
- 端到端验证脚本在 `target/verify/`（gitignored，不进仓库）；内部接口 `/internal/**` 依赖网络边界，
  生产上线需在 Ingress/网关层拒绝外部访问。
