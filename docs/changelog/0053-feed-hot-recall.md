# 0053 · P2 召回多样化：热点（第二路召回）+ 分页游标修复

日期：2026-09-28　前置：0052（抖音式负反馈）

## 一、先做可行性盘点：P2 不是都适合现在做

用户指向 P2（召回多样化 + 更多负反馈信号）。先逐项盘了可行性，<b>不为了"做完 P2"
而硬上会牺牲正确性的方案</b>：

| P2 项 | 结论 | 依据 |
|---|---|---|
| 关注召回 | ⛔ 不做 | 系统<b>没有 follow 关系实体</b>——先要有的关注服务与关注关系表，召回无从谈起 |
| 协同过滤 | ⏸ 推迟 | 需离线 user-item 共现矩阵 + 定时批量；同步在线算要么延迟不可接受、要么拖垮实时链路。属独立工程，另案 |
| 屏蔽作者 | ⏸ 推迟 | `FeedItemView` 契约<b>没有 authorId</b>；加字段要连带 `MediaItem` 全线构造点与历史成员串兼容，风险与本次收益不匹配 |
| <b>热点召回</b> | ✅ 本次做 | 行为数据已在 `PostStatService` 全量汇聚，缺的只是一个有序结构 |
| <b>连刷/重复打散</b> | ⏸ 顺延 | 与热点召回同属读路径改动，分开落便于分别验证回滚 |

结论：本次落<b>热点召回</b>这条真正的新召回通路。它让推荐候选首次不再只来自
「流量池 × 入流时刻」单一维度，而是多了一条「全站热度」来源。

## 二、热点榜：`tf:feed:hot:{yyyyMMdd}`（ZSET）

落在 `PostStatService`（它已经吃全部行为事件，天然汇集点），行为 → 热度权重：

| 行为 | 权重 | 理由 |
|---|---|---|
| SHARE | 2.0 | 传播度是最强信号 |
| COMMENT | 1.5 | 互动成本高 |
| LIKE | 1.0 | 基准 |
| PLAY_COMPLETE | 0.5 | 弱信号（看完≠喜欢） |
| IMPRESSION | **0（不计）** | 只有曝光没有互动不该上榜，否则等于给机器流量发奖 |
| DISLIKE | −2.0 | 快速下榜 |
| NOT_INTERESTED | −3.0 | 同上，更重 |

<b>为什么热点榜不用现有的 stat Hash</b>：热点要「按全站热度取 TopN」，ZSET 天然有序，
一次 `ZREVRANGE` 完成；若用 Hash 存分数再在应用层排序，等于每请求扫一遍当天全部内容。
<b>为什么榜单 member 只存 timelineKey 而非整个成员串</b>：榜单要频繁 ZINCRBY，member 越短越好；
且成员串可能因重复 append（同 score 不同 JSON）而改写，存 id 不会留下与当前时间线不一致的
僵尸成员。代价是召回时多一次 `GET`（O(1) 点查，经 `tf:feed:idx:{timelineKey}` 还原条目）。

## 三、读路径接入（`FeedTimelineStore.readPage`）

- 新增 {@code turbofeed.feed.hot-recall-ratio}（默认 0.1）：每页按该比例给热点留槽位，
  流量池只参与剩下的 `(limit - hotCount)` 个槽位分配 —— <b>单页总量不超限</b>是硬约束。
- **同页去重**：已在热点槽位露出的内容不再占流量池槽位，否则同一页会重复出现同一条，
  还白白吃掉一个曝光位（低池内容的试水机会被挤掉）。
- `hotRecallRatio=0` 完全退化为改造前语义，可作为一键回滚。
- fail-open：热点榜读失败 / 条目还原失败均只跳过该条，不影响其余召回路径。

## 四、顺手修复：分页游标把文章内容整段跳过（致第 1 页返回空）

实现热点召回时发现原有分页游标是错的：

```java
long offset = page * limit;
int start   = per * offset;   // ← 多乘了一次页大小
```

正确应为 `per * page`（本池第 page 页取 `[per*page, per*(page+1))`）。修复前 `page=1` 时
`start = 12 × 20 = 240`，而池内只有几十条 → `start >= end` → 该池<b>整段跳过</b>，
<b>第 1 页直接返回空</b>（此前体感就是"翻页翻着翻着就没了"）。

验证里把它作为硬断言：<b>修复前第 1 页为空，修复后返回紧接第 0 页的下一段</b>。

## 五、验证（`target/verify/HotRecallVerify.java`，真 Redis 集群，11/11 PASS）

- 热度榜排序：分享 > 点赞 > 完播 > 踩（负反馈垫底）；<b>曝光不进榜</b>；
- 热点内容进入当前页并排在首位，<b>同页只出现一次</b>，单页 ≤ limit；
- `hotRecallRatio=0` 后置顶消失（回滚语义成立）；
- 分页：第 0 页 `[hot060..hot049]`、第 1 页 `[hot048..hot037]`，<b>第 1 页非空且两页无重叠</b>
  （该断言在修复前必然失败：当时第 1 页为空）；
- 重复执行可清理、热度榜可归零。

## 六、未决（承接 P2，按确信度排序）

1. <b>协同过滤召回</b>（推迟项）：需离线 user-item 共现矩阵；behavior 事件已具备，缺点播/批处理工程。
2. <b>关注召回</b>（阻塞项）：需先建 follow 关系与服务。
3. <b>屏蔽作者 / 作者维度打散</b>（阻塞项）：`FeedItemView` 需补 authorId 契约，
   并连带 gateway `MediaItem` 构造点改造 + 历史成员串（无该字段）兼容。
4. <b>连刷打散</b>（顺延项）：纯页内重排，风险低，可与下一次读路径改动一并做。
5. <b>P3 排序模型化</b>：`displayScore` 仍是 recency + 完播 + 兴趣 − 负反馈惩罚的线性式。
