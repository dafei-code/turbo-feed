# 0066 抖音式「热度阈值 → 人工复审」闭环（Tier2：越火审得越严）

> 状态：已落地 · 已真实启动验证 · 已端到端验证（tier2_verify.sh 全绿 10/10）  
> 关联：抖音分层审核模型（机审初筛 + 账号信用分级 + 举报/申诉闭环 + 热度复审）；Tier1（0065 举报累计复审队列）；RBAC（CONTENT_REVIEW / CONTENT_TAKEDOWN）；penalty / appeal 体系

## 一、为什么需要（补「热度复审」缺口）

抖音的内容安全是**分层 + 循环持续审核**：机器初审 → 小流量池 → 人工复审 → **热度复审**，  
举报/流量激增会触发重审，**越火审得越严**。Tier1（0065）落地了「举报累计触发人工复审」，  
但还缺第二道闸：**一条已发布内容一旦走红（正向互动暴涨），也应自动进入二次研判**，  
而非只有被举报才复核。

本变更落地三档补强方案中的**第 2 档（热度阈值复审 / 越火审得越严）**：

> 当同一内容的**正向互动累计（点赞 + 评论 + 转发）达到阈值（默认 1000）**&#x4E14;内容仍处于 `APPROVED`，  
> 自动建一条 `PENDING` 复审任务（`review_task` 单表的 `HEAT_ACCUMULATED` 类型），归 `REVIEWER` 二次研判  
> （违规 → 整帖 `TAKEN_DOWN` + 扣分 + 处罚 / 无违规 → 维持发布）。

**与 Tier1 的关系**：共用同一条 `review_task` 队列、`ReviewTaskRepository`、`decideReviewTask` 处置流程，  
仅 `taskType` 不同（`HEAT_ACCUMULATED` vs `REPORT_ACCUMULATED`），CD 复用、不双计。  
第 3 档（流量池分级）仍未做，留待后续。

## 二、设计

- **触发点**：`FeedBehaviorController#report`（行为上报接口）在 `publisher.report` 之外，  
  对批内每条**正向互动**（LIKE / COMMENT / SHARE）逐条调用 `MediaReviewService#onInteraction(postId, type)`。  
  行为上报是用户态主流程，`onInteraction` 失败（含 Redis 不可用）**不影响互动本身**（fail-open，仅 WARN）。
- **热度计数（Redis）**：键 `tf:media:heat:{postId}`，`INCR` 每次正向互动 +1。  
  取 `INCR` 返回值 `count`，**当 `count == heatReReviewThreshold` 时**才触发建单：
  - 精确等于阈值 → 保证「一条走红内容只建一次任务」，并发下至多一个请求命中（其余 `count` 为 ≠ 阈值，跳过）；
  - 不取 `count >= threshold` → 避免越过后每次互动都尝试建单（去重 `existsOpenForMedia` 虽能挡，但等于阈值更省）。
- **postId → 代表行解析**：行为上报只带 `postId`（帖身份 `post/{userId}/{uuid}`），而复审任务以  
  **代表行 `mediaId`** 为对象（整帖一审语义，与 Tier1 一致）。`onInteraction` 经  
  `MediaJdbcRepository#findRepresentativeByPostId` 广播点查 `post_id = ? AND seq = 0 LIMIT 1`  
  解析出代表行，再以其 `mediaId` 建任务。
- **建单三条件**（任一不满足即放弃，防误建/重复建）：
  1. 代表行存在且仍 `APPROVED`（已下架/申诉中不再建任务）；
  2. `INCR` 返回值恰好等于阈值；
  3. 该 `mediaId` 无未决复审任务（`existsOpenForMedia` 去重）。
- **阈值外部化**：`MediaProperties.Review.heatReReviewThreshold = 1000`，键  
  `turbofeed.media.review.heat-re-review-threshold`，可在 `application.yml` 调参，不写死在代码里。
- **任务模型**：复用 `ReviewTask`（record），新增类型常量 `TYPE_HEAT_ACCUMULATED = "HEAT_ACCUMULATED"`；  
  `triggerCount` 字段填触发时的热度值（如 1000），便于复盘。
- **处置复用（与 Tier1 完全一致）**：`decideReviewTask` → `takedown=true` 走  
  `takeDownAndPenalize`（CAS 翻 `APPROVED→TAKEN_DOWN` + 移出时间线 + 扣信用 + 落处罚）
  - `resolveAllForMedia(TAKEDOWN)`，CAS 保证并发/重复处置幂等、不双计；  
    RBAC：`review-task/list` 需 `CONTENT_REVIEW`、`review-task/decide` 需 `CONTENT_TAKEDOWN`  
    （`REVIEWER` / `ADMIN` 均具备，`resolver` 取当前登录用户）。

## 三、存储取舍

- 复用 Tier1 的 `review_task` **SINGLE 单表（落 ds_0 = turbo_feed_1）**，**无新增 DDL**：  
  `taskType` 为 `VARCHAR`，`HEAT_ACCUMULATED` 与 `REPORT_ACCUMULATED` 共用同表，按 `status` 扫描全貌。
- 热度计数**不落库**：存 Redis（`tf:media:heat:{postId}`），实时、可随 key TTL/淘汰自然清理，  
  与内容安全「二次研判」语义解耦——计数只是触发信号，任务一旦建出即以 DB 为权威。

## 六、环境注意

- 阈值调参改 `turbofeed.media.review.heat-re-review-threshold`，无需改代码重编译。
- `review_task` 单表仍只落 ds_0；扩容/分库迁移随 Tier1 一并处理。
- **本地 Redis 集群组群坑（已踩已修）**：本机 6 节点容器 `redis-7000..7005` 的  
  `cluster-announce-ip` 曾被配成 `192.168.0.6`（本机不可达）→ `cluster_state:fail`、gossip 不收敛；  
  手动组群时若错配成 `127.0.0.1`，容器内部 `127.0.0.1` 指向自身，节点间同样互连不上。  
  **正确值 = 本机真实 LAN IP（`ipconfig getifaddr en0`，本次为 `192.168.0.3`）**，容器经 Docker 转发互访、  
  网关宿主 JVM 也能解析。修复步骤：`CONFIG SET cluster-announce-ip 192.168.0.3`（6 节点）→  
  `FLUSHALL` + `CLUSTER RESET HARD` → `redis-cli --cluster create 192.168.0.3:7000..7005 --cluster-replicas 1 -a 123456`。  
  网关启动早于 Redis 可用会留下 stale Lettuce 拓扑，需重启网关刷新（kill 8080 后重跑 `run_gw_tier1.sh`）。
- 端到端验证脚本在 `target/verify/`（gitignored，不进仓库）。
