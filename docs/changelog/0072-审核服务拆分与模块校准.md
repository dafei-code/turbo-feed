# 0072 · 审核上帝类拆分 + 模块形态校准（#310 / #312）

- **状态**：已完成（代码 + 单测，本地 `test-compile` 通过；运行时单测由 CI 验证）
- **优先级**：P1-1（#310 可维护性：消除 `MediaReviewService` 上帝类）+ P1-3（#312 模块割裂误判校准）
- **关联**：changelog 0037（P0-3 发件箱同事务）、0065/0066/0067（举报累计 / 热度复审 / 流量池分级）、ADR-0004（tf-hotspot SDK）

## 为什么做

- **#310**：`MediaReviewService` 是 1014 行的上帝类——24 个依赖、13 个 public 方法，内聚 7 簇职责
  （机审初筛 / 人审 / 举报 / 申诉 / 梯度处置 / 热度-池晋级加严 / 时间线投递），任何一处改动都牵一发动全身，
  回归测试只能覆盖 CAS 这一角。把它按职责边界下沉为协作子服务，门面只保留 API 契约与事务边界。
- **#312**：此前误判 `tf-hotspot` 为空壳、把"模块割裂"风险落在它身上。实测 `tf-hotspot` 已落地
  （ADR-0004：零 Spring 依赖 SDK + 8 单测 + 引擎第二消费者 `HotTimelineKeyCache`），真正的空壳是
  `tf-benchmark`（仅 `.gitkeep`，零 `.java`）。文档须校准，避免误导后续拆分决策。

## 设计（#310 审核服务拆分）

拆为 **3 个无状态协作 Bean + 1 个门面**，依赖单向、无循环：

| 子服务 | 职责 | 关键依赖 |
| --- | --- | --- |
| `ReviewTimelineDelivery` | 审核状态 ↔ 公域时间线可见性：入流 / 摘除 / 缓存失效 / 整帖解析 / `parseUserId` | mediaRepository / mediaTagRepository / redisTemplate / outboxService |
| `ViolationDispositionService` | 确认违规 → 梯度处置：`applyDisposition` 按 `DispositionPolicy` 分发 `MONITOR`（限公域）/ `INTERCEPT`（下架+扣分+落处罚）+ `healthTier` | 上述 + accountHealth / moderationSignal / behaviorLog / dispositionPolicy / accountCredit / penalty / properties / storageClient + `ReviewTimelineDelivery`（下架摘除时间线） |
| `ReviewEscalationService` | 抖音式「越火审得越严」「流量池晋级加严」「同类举报累计→人工复审」 | mediaRepository / redisTemplate / contentModeration / reviewProperties / reportRepository / reporterCreditService / reviewWaterLevelService / reviewTaskRepository + `ViolationDispositionService`（晋级复扫命中走处置） |
| `MediaReviewService`（门面） | 保留 13 个 public 方法 + `@Transactional` 边界 + CAS 翻转语义，内部委托三子服务 | 3 子服务 + 门面自身仍需的 mediaRepository / redisTemplate / contentModeration / reviewProperties / accountCredit / reportRepository / appealRepository / reviewTaskRepository / outboxService / penalty / reporterCredit / reviewWaterLevel / behaviorLog / moderationPolicy |

**对外行为零回归**（核心约束）：
- 13 个 public 方法签名、事务边界（`@Transactional`）、CAS 幂等语义**完全保留**——调用方（Controller / 引擎 / 事件消费者）无感。
- 子服务方法都在门面事务内执行，自身**不声明事务**，保证发件箱事件行与状态翻转写在同一个本地事务
  （changelog 0037 / P0-3），不引入"幽灵消息"或"内容已可见却没进时间线"。
- `reviewByMediaId` 沿用改造前 inline 落发件箱事件写法（不含内容标签冷存写），与历史行为一致；
  `handleAppeal` 走 `delivery.publishAppend`（含标签冷存），与原实现一致——两处差异在改造前即存在，本拆分不扩大。

## 风险与未决

- **默认零行为变更**：门面方法签名 / 事务 / CAS 语义完全保留，未改任何对外契约。
- **DI 拓扑**：`disposition → delivery`、`escalation → disposition` 单向无环；三子服务 `@Service` 无状态，
  与门面同 Spring 上下文，构造器注入确定。
- **#312 未决（可选）**：`tf-benchmark` 空壳模块是否从根 pom 移除——当前仅文档标注删除条件，留待引入正式压测方案或确认废弃时执行，不在本次范围。
