# 0085 内容安全 Phase 0：指标接入 + NFKC 快路径 + SLO 基线

> 状态：已落地 · 单元测试全绿（新增 `TextNormalizerTest` 18 项）
> 关联：`docs/ops/content-security-slo.md`（本文档建立的口径）；ADR-0013 / ADR-0014（REVIEW/LIMIT 下游处置）

## 一、为什么做

内容安全模块此前已达到「设计工业级」，但**工程保障差一档**：2,528 行只有 14 个单测、零集成测试，且关键指标没有任何出口。规模演进的所有决策（要不要换 DAT、要不要拆服务、缓存该不该加）都依赖"当前 P99 多少、词库多大、误杀率多少"——没有这些数字，任何优化都是盲改。

本次落地演进计划的 **Phase 0「先建立度量」**，并顺手做了 Phase 1 里收益最高、风险最低的一项（NFKC 快路径）。

## 二、改了什么

### 1. 指标接入（Phase 0 核心）

`ContentSecurityService` 新增 `ModerationMetrics` 内部门面，接进**既有的** Micrometer → `/actuator/prometheus`（`tf-gateway/pom.xml` 早已引入 `micrometer-registry-prometheus`，此前只是敏感词模块没注册）。

四个指标：

| 指标 | 类型 | 用途 |
|---|---|---|
| `content_security_check_total{scene,action}` | Counter | 检测量、命中分布、豁免比例 |
| `content_security_check_duration_nanos` | DistributionSummary | P50/P95/P99 延迟 |
| `content_security_dict_size` | Gauge | 已加载词条数（**0 = 过滤失效**） |
| `content_security_dict_age_seconds` | Gauge | 距上次成功重建秒数（持续增大 = 热更新卡住） |

**设计取舍**：用 `ObjectProvider<MeterRegistry>` 而非直接注入。单测用 `@InjectMocks` 构造本类时容器里没有 `MeterRegistry`，直接注入会拿到 null 并在每次计数时 NPE。通过 provider 取、缺失则退化为 no-op——可观测性是**可选增强**，不该让核心拦截逻辑硬依赖它。

**实现细节**：`check()` 抽出 `doCheck()` 内层，在入口统一计时与记录，而不是在 4 个返回出口逐个插桩（易漏记）。对外行为零变化。

`SensitiveWordService` 补 `lastLoadedAt()`（与 `WhitelistService` 同构），供 `dict_age_seconds` 使用。

### 2. NFKC 快路径（Phase 1 先手）

**问题**：`TextNormalizer` 主循环里每个字符都调一次 `Normalizer.normalize(String.valueOf(c), NFKC)`——一条 2048 字 caption 就是 2048 次 ICU 调用。

**依据（实测，JDK 17）**：
- CJK 统一汉字基本区 `U+4E00–U+9FFF` 共 20,992 字，NFKC 后**全部恒等**
- ASCII 可打印区 `U+0020–U+007E` 同样**全部恒等**
- 会变化的是兼容字符：`㈱→(株)`、`㍿→株式会社`、`①→1`、`Ａ→A`、`ﬁ→fi`、`Ⅻ→XII`

**改法**：新增 `nfkcIdentity(char)` 判定，命中则跳过 ICU 直接取原字符。中文为主的实际文本里 ICU 调用降到接近 0。

**为什么不用「整串 NFKC + 反推映射」**：那需要重建"归一化下标→原文下标"映射，极易破坏"㈱ 一变多时整段高亮"的既有语义。当前方案**下标映射逻辑一行未改**，输出与逐字符 NFKC 完全一致，零正确性风险。

**覆盖边界（诚实标注）**：只覆盖基本区与 ASCII。CJK 扩展区生僻字、日文假名、韩文走 ICU 路径——正确性不受影响，只是少了这项优化。

### 3. 测试护栏（16 → 34 项）

新增 `TextNormalizerTest`（18 项），核心是**等价性对拍**：测试内独立重写一遍优化前的逐字符逻辑作为参照（刻意不调用被测方法，否则恒真），断言「优化后输出 == 参照实现输出」。一旦 `nfkcIdentity` 边界写错、该折叠的没折叠，测试立刻红——因为那是"敏感词漏放且接口看不出异常"的静默失效风险。

同时覆盖：下标回溯（含被剥掉的分隔符、一变多字符共享下标、越界返回 -1）、null/空串、繁简折叠、拼音折叠。

### 4. SLO 文档

新增 `docs/ops/content-security-slo.md`：6 条 SLO、4 条 Prometheus 告警规则、压测基线记录表、**以及"什么指标触发下一阶段"的映射表**——把"何时该做更重的改造"从架构直觉变成可观测的决策。

其中 `ContentSecurityNoHits` 告警（词库非空但一小时零拦截）价值最高：捕获"看起来正常、实际全被绕过"的静默失效。

### 5. 压测场景调整

`tf-benchmark` 的 `comment-publish` 场景正文从 `"bench-N"`（约 8 字符）改为约 200 字符中英混排。

**为什么必须改**：8 字符的评论会被检测链路极快扫过，**测不出归一化的真实成本**（成本随长度线性增长）。短文本压测会系统性低估检测开销，让人误以为"检测很便宜"，从而低估优化必要性。

## 三、顺带修掉的一个真实缺陷

写等价性测试时发现：`PinyinTable` **漏了「涉」字**。

「涉」是「涉黄」「涉政」「涉毒」「涉赌」四个词族的公共前缀——漏了它意味着这整族词的拼音绕过（`shehuang` 等）全部拦不住。已补充「涉/造/谣/传/播/散/恐/吓/威/胁/勒/索」等词族高频字。

这是测试驱动发现的问题，不是预先知道才补的。

## 五、下一步（未做）

按 `docs/ops/content-security-slo.md` 的阶段映射，Phase 1 剩余项：

1. **检测结果两级缓存**（key 必须含词库版本号，否则更新后命中旧裁定）
2. **单用户检测限流**（超限降级为异步检测，而非拒绝发布）
3. **3 条集成测试**（词库加载端到端 / 热更新链路 / 分级动作端到端）
4. **误杀申诉闭环**（被拒返回 verdictId → 用户申诉 → 人审 → 自动加白名单）

其中集成测试优先级最高：现有 34 个单测全是纯逻辑验证，**没有一条走过"真实 MySQL → 词库加载 → AC 匹配 → 裁定"的端到端路径**，而单测证明不了"SQL 写错导致词库静默为空"。
