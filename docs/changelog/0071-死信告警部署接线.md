# 0071 · 死信（DLQ）积压告警部署接线（P0-2）

- **状态**：已完成（代码 + 单测，本地未推送）
- **优先级**：P0-2（时间线投递可靠性的运维闭环：死信不再静默积压）
- **关联**：P1-PR02 DLQ 死信重放管理接口（`FeedTimelineDlqService` / `RocketMqDlqStore` / `FeedTimelineDlqController`）

## 为什么做

此前死信进入 DLQ（`%DLQ%{consumerGroup}`）后只静默积压，要等运维人工跑 `dlqList` 才发现——
等于"内容事故靠人盯"。本改动把"DLQ 非空即报警"做成**定时巡检**，让死信积压第一时间触达值守
（日志 ERROR + 可选 webhook），发现时效从"人工轮询"降到"秒级自动"。

## 设计

- **触发口径**：当前 DLQ 积压条数 `>= threshold` 且距上次告警已过 `cooldown-ms` 才发。
  - 阈值防误报（偶发 1 条不必惊动）；冷却防告警风暴（积压未消时每轮都报会刷爆渠道）。
  - 巡检间隔 / 阈值 / 冷却 / 样例上限 / 实例标识 / webhook 全部配置化，部署按预案接线。
- **fail-open**：巡检自身异常只告警、绝不抛；告警出口（`LogWebhookDlqNotifier`）同样 fail-open
  （webhook 未配→只打日志；webhook 配但失败→仅 warn，日志仍留痕）。告警本身绝不拖垮时间线主链路。
- **生命周期**：仅在 `dlq-alert.enabled` + `dlq-replay.enabled` + `mq.enabled` 同时为 true 时注册
  （前两者缺任一，`RocketMqDlqStore` 巡检消费者都不存在，告警无从读起）。
- **出口解耦**：`DlqAlertService` 只判定+生成 `DlqAlert`，发出动作交给 `DlqNotifier`
  （默认 `LogWebhookDlqNotifier`：日志 + 可选 `java.net.http.HttpClient` POST；测试注入记录型实现验证触发逻辑）。
- **不新增依赖**：webhook 用 JDK 自带 `HttpClient`，不引 rest 客户端。

## 部署接线（配置键，默认全关，需部署开启）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `turbofeed.feed.timeline.dlq-alert.enabled` | false | 总开关（须与 dlq-replay + mq 同开） |
| `turbofeed.feed.timeline.dlq-alert.threshold` | 1 | 触发告警的最小积压条数 |
| `turbofeed.feed.timeline.dlq-alert.check-interval-ms` | 60000 | 巡检间隔（@Scheduled fixedDelay） |
| `turbofeed.feed.timeline.dlq-alert.cooldown-ms` | 300000 | 同一条告警最小重发间隔（5min） |
| `turbofeed.feed.timeline.dlq-alert.sample-limit` | 20 | 告警 payload 携带的样例 mediaId 上限 |
| `turbofeed.feed.timeline.dlq-alert.webhook-url` | 空 | 告警 webhook（留空=仅日志；填则 POST JSON） |
| `turbofeed.feed.timeline.dlq-alert.engine-id` | 空 | 多副本部署时区分来源（建议填实例/ pod 标识） |

webhook JSON：`{"alert":"FEED_TIMELINE_DLQ","engineId":...,"count":N,"timestamp":...,"samples":[...]}`

> 现有管理接口 `GET /api/v1/admin/feed/timeline/dlq`（网关 `AdminFeedTimelineDlqController`）已能
> 看到死信列表与条数，运维可据此复核；本改动补上"自动告警"这一环。告警状态查询端点为可选增强，未做。

## 风险与未决

- **默认全关**：不配 `dlq-alert.enabled=true`（且 dlq-replay/mq 同开）则本服务不注册，与现状一致，零行为变更。
- **webhook 是旁路**：发送失败仅 warn，不影响时间线主流程；日志 ERROR 始终留痕，运维仍可从日志侧发现积压。
- **未决（可选增强）**：告警状态查询端点、`lastAlertAt` 暴露到 metrics。当前已满足"自动发现死信积压"的核心诉求。
