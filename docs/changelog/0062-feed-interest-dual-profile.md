# 0062 长短期双层画像 —— 长期层定"你是什么样的人"，短期层定"你现在想要什么"

- 日期：2026-09-29
- 影响模块：`tf-feed-engine`（`InterestService`）
- 类型：新增能力；新增配置 `turbofeed.feed.interest.short-term.*`（全部有默认值，`enabled` 可一键关回单层）
- 验证：`InterestDualProfileVerify` 24/24；全套回归 126 PASS / 0 FAIL；端到端 8/8

---

## 一、为什么 0061 的衰减还不够

0061 给画像加了**半衰期衰减**，解决了"三年前的兴趣永远压过现在的兴趣"。
但它仍然只有<b>一层</b>——半衰期取 14 天意味着它是一个**慢变量**。这会漏掉一类非常真实的用户行为：

> 用户连着刷了 20 条钓鱼视频，然后第二天又刷了 20 条露营视频。

在单层模型里，"钓鱼"这 20 次行为的贡献要经过好几天才衰减到一半，
而"露营"作为新兴趣**根本挤不进 TopN**——它被历史均值稀释了。
用户当下的诉求没有得到响应，体感就是"推荐越来越不准"。

抖音为此把兴趣画像明确分成两层：**长期兴趣**（慢衰减，刻画稳定偏好）
与**短期兴趣**（快衰减，刻画最近 burst），两者分别参与召回。
本期就是把这分层落到我们的画像上。

## 二、实现

### 结构：两个 key，同一套存储格式

```
长期层  tf:user:interest:<userId>         半衰期 14 天    TTL 30 天
短期层  tf:user:interest:recent:<userId>  半衰期 12 小时  TTL 7 天
```

两层的存储格式完全一致（都是「tag → 衰减后权重」的 Hash + `__ts__` 哨兵），
复用 0061 的同一份 Lua 脚本，只是传不同的 key / 半衰期 / TTL。一次行为**同时喂两层**。

**为什么是两个 key 而不是在一个 Hash 里加前缀/后缀**：同一个 Hash 只有一个 `__ts__`，
而两层要各自用不同的速率做整体衰减；塞进一个 Hash 就得做成"每 tag 一个时间戳"，
存储翻倍且 Lua 复杂度陡增。两个 key 各自一次 `EVAL`（每次只碰一个 KEY），
因此不触碰 Redis 集群的 CROSSSLOT 限制——这一点很关键，否则又要改键名。

**两次 EVAL 之间没有原子性**：它们改的是两个不同的 key，各自内部原子即可。
丢一次短期累加的损失，远小于让写路径串行等待两次执行完成。

**为什么短期层还要单独 TTL 7 天**：半衰期只让数值趋近 0（配合 `min-score` 会清掉大多数标签），
但 TTL 才是"用户彻底不来了就把整份短期画像删掉"的兜底，避免库里留一堆只剩哨兵字段的 Hash。

### 融合：先各自归一化，再加权相加

```java
relLong  = longTerm.getOrDefault(tag, 0.0)  / maxLong
relShort = shortTerm.getOrDefault(tag, 0.0) / maxShort
score    = longWeight * relLong + shortWeight * relShort
```

**为什么必须先归一化**：两层的**量纲完全不同**。长期层按 14 天半衰期累积，稳态值可能是几十；
短期层只累积最近半天，稳态值通常个位数。若直接 `long*k1 + short*k2` 相加，
短期层的贡献会被长期层的绝对值淹没，权重系数也就失去可解释性——
调 `k2` 时完全不知道调到哪算够。归一化到 [0,1] 之后，
融合权重的含义退化成纯粹的"相对重视程度"，**好调也好解释**。

### 融合结果只用于召回，不用于排序加权

这是本期最需要说清的边界：

| 环节 | 用什么 | 为什么 |
|---|---|---|
| **召回选标签**（决定"能看到什么"） | 融合后的 `recallTags` | 短期兴趣的第一诉求是**拿到召回位**——否则连出现的机会都没有 |
| **排序加权**（决定"谁排更前"） | 长期层原始权重 `weightedTags` | 量纲真实、可解释；排序交回长期信号更稳 |

这样分还有个直接收益：**0060 / 0061 的语义与断言一个字都不用改**。
`weightedTags` 仍然返回"长期画像的原始权重"，所有既有验证脚本照跑。

### `hasInterest` 也要看短期层

新用户可能长期层还没攒起来（没到两次写入或已被 `min-score` 滤掉），却已经有短期行为。
这时他明明有可个性化的依据，不该按冷启动处理。
实现上先用 O(1) 的 `HLEN` 判长期层，**只有长期层为空时**才多看一次短期层，
绝大多数活跃用户走不到第二步。

## 三、配置

```yaml
turbofeed.feed.interest:
  short-term:
    enabled: true            # 关闭后退化为 0061 的单层画像
    half-life-hours: 12      # 短期半衰期：半天不碰，这次突发兴趣衰减一半
    long-weight: 1.0         # 融合时长期层的相对权重
    short-weight: 2.0        # 融合时短期层的相对权重（默认比长期更受重视）
```

`short-weight` 调到 0 → 短期层只影响"有无"、不影响排序；`enabled=false` → 整体关回单层。

## 四、验证

### 核心证据：同一份数据上出现"排序翻转"

构造一个现实场景：用户长期爱看钓鱼（`fish=10.0`），刚才顺手点了一条做饭（`cook=1.0`）。

| 视角 | 第一名 | 说明 |
|---|---|---|
| 长期层 `weightedTags` | **fish** (10.0) | 单层画像的结论：长期爱好遥遥领先 |
| 融合后 `recallTags` | **cook** (2.1 vs fish 1.0) | **翻转**：短期 burst 抢到了召回位 |

计算过程刚好可手算校验，这正是选这组数字的原因：

```
fish: relLong=10/10=1.0, relShort=0/1=0.0 → 1.0*1.0 + 2.0*0.0 = 1.0
cook: relLong= 1/10=0.1, relShort=1/1=1.0 → 1.0*0.1 + 2.0*1.0 = 2.1
```

**同一份数据、同一个用户，单层与融合给出相反的结论**——这就是"短期层确有其必要"的直接证明，
不需要靠"感觉上更准"。

## 五、踩坑

- **新增存储 key 时，必须同步所有"清理点"**：加了短期层之后，
  `InterestDecayVerify` 的「⑩ 清理完成」立刻红了——它只删 `tf:user:interest:<u>`，
  短期层残留导致 `hasInterest` 仍为真。已给 6 个相关验证脚本
  （Decay / Weight / Recall / NegativeFeedback / RecCache / Phase1b）**成对补齐**短期键清理。
  **这不是测试脚本的小毛病，是双写结构引入的必然成本**：
  凡是"增加一个附属 key"的改动，第一步就该全局搜现有 delete 点。
- **两层之间的距离会被"长期层被删"测试污染**：本次一度把"只有短期层"的场景写在前面，
  导致后续"两层都在"的召回断言失败（`⑦c`）。单测内部的场景顺序也是隐式依赖，要留意。

## 六、未完成（下一步）

- **短期层目前只影响召回选标签，还没进精排**。真正的抖音在排序模型里也会用短期行为序列
  做实时特征（例如最近点击的内容序列直接喂给双塔/精排）。我们这里排序仍只吃长期权重，
  所以"短期兴趣的内容会**出现**，但不一定排在**最前**"。
- **session 级序列建模**：现在短期层是"标签累积 + 快衰减"，还没有"用户在一次会话内的行为顺序"
  这种更强的信号（抖音的双塔召回里，短期序列通常直接做 target-attention）。
  要落这一条，需要先把 0062 的短期画像接进 `RankingModel` 的特征输入。
