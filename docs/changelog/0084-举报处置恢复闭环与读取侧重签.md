# 0084 · 举报处置恢复闭环、条件解除原子化与推荐流读取侧重签

- **状态**：已完成（双模块全量门禁绿：网关 323 通过 / 0 失败 / 8 跳过，引擎 222 通过 / 0 失败；**真启动联调未做**，见文末诚实边界，2026-11-08）
- **优先级**：P0 修正（承接 0083 / ADR-0014 §5 登记的遗留项）
- **关联**：0082、0083、[ADR-0014](../adr/0014-content-demote-and-signal-lifecycle.md)、[ADR-0015](../adr/0015-signal-release-atomicity-and-readside-resign.md)、0008（公域时间线边界）

> 0082 / 0083 是历史快照，本文件不修改它们。本轮**不改跨服务契约**：`tf:mod:media.action` 的枚举与消费语义仍与 `460ed15` 一致，无数据迁移。

## 为什么做

`0083` 交付时列出的「待办与诚实边界」逐项核对后，确认三处是真实缺陷、一处是并发窗口、一处需运营数据，外加一条前序遗留：

| 编号 | 问题 | 症状 |
| --- | --- | --- |
| G1 | `softLimit` 摘时间线后，判无违规只清 `tf:mod:media`，不重投公域 | 搜索恢复可见、发现流仍缺该帖；`tf:media:disposition` 标记永久残留 |
| G2 | `handleAppeal(upheld=true)` 翻案不清 INTERCEPT | 申诉赢了，召回层/搜索层仍硬剔除，最长 30 天 |
| G3 | `clearDemotionIfPresent` 读 + 删两步非原子 | 并发升级 MONITOR/INTERCEPT 时，改一次描述即可抹掉隔离/下架信号 |
| G4 | 公域推荐流读取侧未现签 | 引擎物化的是投递时刻的预签名 URL，私有桶下 900 秒过期 → 整页 403 |
| G5 | `0.7 / LOW / MID` 无运营校准口径与发布清单 | 灰度只能靠拍脑袋，无观察项与回滚线 |

实现中另发现并收紧两个回归风险：**R1**（统一恢复会破坏「只有 CONTENT_REVIEW 才清信号」的 ADR-0014 语义）、**R2**（先删标记后投递，Redis 删除不随 DB 事务回滚 → 恢复不可重试）。详见 ADR-0015 §1。

## 改动

### 举报处置域（G1 / G2）

| 文件 | 改动 |
| --- | --- |
| `ViolationDispositionService` | `clearContentSignal` 扩为人审判无违规 + 申诉翻案共用；新增 `restoreAfterNoViolation(mediaId, authorId, taskType)`：**状态闸门（仅 APPROVED）→ 任务类型闸门 → softLimit 标记闸门 → 清信号 → 重投时间线 → 最后删标记** |
| `MediaReviewService` | `decideReviewTask(takedown=false)` 统一委托恢复并透传 `task.taskType()`；`handleAppeal(upheld=true)` 在 CAS 成功分支、**重投之前**清 INTERCEPT |

恢复动作的关键性质：

- **幂等**：只有 `tf:media:disposition:{key}=MONITOR`（确实被摘过）才 append；标记删除后重复判定不会二次投递。
- **不误放**：`TAKEN_DOWN` 直接返回且连信号都不清；非 `CONTENT_REVIEW` 任务且无标记时不碰任何 Redis 键。
- **可重试**：标记最后删，投递失败/事务回滚时保留标记供 OutboxRelay 或下次判定补偿；`post` 视图为空也保留标记。
- **键口径**：有 `postId` 用 `postId`，历史单图帖回退 `mediaId`，与 `softLimit` 写入完全一致。
- **整帖视图**：`delivery.asTimelinePost` 补齐多图，池层级取 `accountCreditService.ensure(...).poolLevel()`，与审核通过 / 翻案同一套路。

### 条件解除原子化（G3）

`ModerationSignalService.clearDemotionIfPresent` 从 Java 侧 `HGET` + `DEL` 两步改为一次单键 Lua `EVAL`：

```lua
local action = redis.call('HGET', KEYS[1], 'action')
if action == ARGV[1] then return redis.call('DEL', KEYS[1]) end
return 0
```

只访问 `KEYS[1]`（Redis Cluster 单 slot 兼容），目标值由 `ARGV[1]` 传入，返回 1=已删 / 0=未删；fail-open 不变。**判定权完全在 Redis 侧**：改描述 PASS 永远只能解除轻降权。

### 推荐流读取侧重签（G4）

| 文件 | 改动 |
| --- | --- |
| `MediaUrlResolver` | 新增 `resolveFromUrl` / `extractMediaId`：从已物化的 URL 反推 `media/{userId}/{uuid}.{ext}` 并复用 `resolve` 现签；非 minio 或反推失败**原样返回** |
| `FeedItemMapper` | 新增 `toView(item, UnaryOperator<String> rewriter)` 重载，逐条重写 `url` / `imageUrls`；无参重载保留 |
| `FeedEngineClient` | 注入 `MediaUrlResolver`，推荐流映射传 `urlResolver::resolveFromUrl`（构造器 +1 参，已确认全仓无手动 `new`） |

为什么不改契约 / 不回查 DB：`FeedItemView.imageUrls()` 是 URL 列表而非 mediaId 列表；加字段要迁历史 Redis 成员串，逐帖回查 DB 会给热路径加 N 次分片查询。反推是零迁移、零 DB 查询方案，代价是依赖对象名格式（见 ADR-0015 §3）。

### 运营校准与发布清单（G5，规划中未实施）

> **规划中未实施**：以下为口径与 checklist，不代表已调参或已灰度。完整版见 ADR-0015 §2.5。

- 依赖指标：LIMIT 内容曝光占比/CTR/完播率、REVIEW 人审通过率与时延、改描述 PASS 后 24h 复发率、判无违规后二次举报率、申诉翻案率、`tf:mod:media` 残留分布。
- 调参：单集群灰度 5% → 观察 24h → 一次只动一个参数 → 再观察 24h → 扩量。
- 回滚线：核心指标偏离基线 > 15%，或出现「改描述绕过隔离」「翻案后违规复现」→ 把 `enable-content-demotion=false` 或把系数回调到 1.0，不回滚代码。
- 配置键：`enable-content-demotion=true`、`content-demote-scale=0.7`、`default-limit-severity=LOW`、`default-review-severity=MID`、`media-ttl-seconds=2592000`。

## 发布 / 回滚

1. **网关先、引擎后**。本轮改动不涉及 `tf:mod:media.action` 新枚举值，跨服务契约与 `460ed15` 完全一致，**无需数据迁移**；引擎本轮零代码改动。
2. 先发网关：举报恢复闭环、Lua 原子化、读取侧重签都是网关侧；旧引擎不认新逻辑也不受影响。
3. 再确认引擎已全量 `460ed15`（DEMOTE 消费）。灰度期若有旧引擎实例未升级，DEMOTE 会退化为「**不降权但可见**」——方向安全（宁可少降权，不可误剔除），无需回滚。
4. 观察项：推荐流图片 403 率（应为 0）、`tf:mod:media` 残留数、判无违规后时间线回补成功率、申诉翻案后搜索可见率。
5. 回滚：读取侧重签异常可先切非 minio 原样透传路径或整体回滚网关；Lua 脚本退回两步读删虽恢复竞态但功能等价，属可接受降级。
