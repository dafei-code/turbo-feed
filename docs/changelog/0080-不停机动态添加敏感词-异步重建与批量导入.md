# 0080 · 不停机动态添加敏感词（后台异步重建 + 单飞 + 批量导入）

- **状态**：已完成（tf-gateway 编译 + 14 个 moderation 单测全绿，2026-10-30）
- **优先级**：P0 配套（评审「敏感词子系统」收尾项：动态添加的管理面延迟）
- **关联**：0028（内容安全地基）、0079（P0 全部命中 + 严重度决策）、0031（admin 默认拒绝）

## 为什么做

「不重启、不停机」原本就具备——`Dictionary`(AC + 分类表) 由单个 `AtomicReference` 持有，
后台构建新快照后整体 CAS 切换，读路径零锁零阻塞。但 admin 的 `add/disable/enable/delete`
走的是**同步** `reload()`：全量 `findAllEnabled()` + 重建整个 AC 在 **HTTP 线程内**完成。
按 `AhoCorasick` 实测（1M 词全量重建 1.2s），大词库下：

- `POST /admin/moderation/words` 一个调用要阻塞 ~1.2s；
- 批量一个个加 100 个词 → 触发 100 次全量重建（冗余 ~120s）；
- 并发管理操作各自重建，纯浪费。

读路径虽不停机，**管理面本身会被大词库卡住**。本改造让「动态添加」对管理面也零阻塞。

## 改动

| 层 | 文件 | 改动 |
| --- | --- | --- |
| 匹配层 | `SensitiveWordService` | 新增**单飞异步重建** `triggerReload()`：admin 变更只写 DB + 触发后台线程重建（fire-and-forget，HTTP 立即返回）；单飞串行 + 指纹追平（最多 3 轮）保证最终一致。`add/disable/enable/delete` 改调 `triggerReload()`；`reload()` 保留为同步强制刷新（供 `/reload` 与启动 `init`）。新增 `shutdown()`（`@PreDestroy` 关线程池） |
| 持久层 | `SensitiveWordRepository` | 新增 `batchUpsert(List<String> words, String category)`：一条批处理 SQL 完成 N 条 upsert，返回写入条数 |
| 入口 | `AdminSensitiveWordController` | 新增 `POST /admin/moderation/words/batch`（`@RequestBody List<String> words` + `category`）：一次 DB 批处理 + 一次后台重建；类注释更新「立即触发」→「后台异步」 |

### 单飞异步重建算法（`triggerReload`）

```
if !reloadInFlight.CAS(false, true): return   // 已在飞行中，本轮变更会被追平
reloadExecutor.submit(() -> {
    do {
        doReload(null)                        // 读最新 DB 建新快照 + dictRef.set 原子切换
        guard++
    } while guard < 3 && !checkSum().equals(lastCheckSum)  // 重建期间有新变更则再追一轮
    reloadInFlight.set(false)
})
```

- **单飞**：并发/快速连续触发只提交一次任务，避免 N 次全量重建。
- **追平**：进行中的重建读的是触发时刻的 DB；若重建期间又有新写入，完成后比对指纹，
  最多再追 2 轮，保证「最后写的那条词」一定进入下一个生效快照——既不被漏、也不重复建。
- **零阻塞**：HTTP 线程只在 DB 写入后返回，AC 重建耗时（与词库大小成正比）完全在后台。

## 影响面核查

- `reload()` 仍是同步公共方法，签名未变，`@PostConstruct init()` 与 `/reload` 接口行为不变。
- `add` 等返回类型未变（`add` 仍返回 DB 的 `SensitiveWord`；`batchAdd` 返回条数）。
- 读路径 `matchAll` 只依赖 `dictRef.get()`，本次未改动其语义。

## 未做留白（诚实边界）

- **批量接口按统一 category 导入**：逐词不同分类需改 `@RequestBody` 为 `{word, category}[]` 结构，当前刻意从简（运营「整批导入某分类词库」为主场景）。
- **`triggerReload` 单测未做并发压测**：单飞/追平逻辑仅靠上述轮询单测与代码推演验证；高并发批量 add 的最终一致性建议后续用集成测试（需 H2/真实 MySQL）补强。
- **增量更新（不重建全量 AC）**：本改造解决了「管理面阻塞」，但未做「只把新词增量插入已有 AC」——
  那是下一档优化（词库 1M+、且每秒多次动态加词时才值得；当前全量重建 1.2s 已在后台，可接受）。
