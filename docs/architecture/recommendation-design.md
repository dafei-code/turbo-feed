# 推荐与用户画像设计蓝图（分表数据的聚合分析）

> **规划中未实施**——本文档是设计蓝图，不含任何已落地代码。
> 目标问题：后续要按用户画像推送视频，而业务库已分库分表（2 库 × 128 物理表），
> 「跨分片聚合分析」与「在线事务」是两种冲突的负载。

## 0. 结论先行

1. **分片库不为分析改造**。OLTP 库继续只服务事务（点查 + 短事务），分析负载整体出仓——
   这是本方案最重要的承诺：media/comment 等表的分片结构、索引、连接池都不会为推荐动一刀。
2. 出仓管道：**binlog CDC → RocketMQ（已有）→ ClickHouse 列存 → 画像标签 → Redis 在线特征**。
3. 推荐不推翻现有 feed-engine 的 ZSET 池化时间线，而是**叠加「召回 + 重排」层，并把时间倒序保留为降级通道**。
4. 分四期落地，P0 零新组件。不要一上来就 Flink / K8s / 向量库。

## 1. 问题：为什么分表之后「聚合分析」变成一个独立问题

| 维度 | OLTP 分片库擅长的 | 画像/推荐需要的 |
|---|---|---|
| 查询形态 | 按分片键点查（user_id / media_id 精准命中单分片） | 跨用户扫描、多维 GROUP BY、时间窗口、多表 join |
| 数据组织 | B+Tree 行存，为「取一行」优化 | 列存，为「扫一列算聚合」优化 |
| 读放大 | 单分片 O(1)~O(log n) | 聚合一次 = fan-out 全部 2×128 张物理表再归并 |
| 在线影响 | — | 大扫读污染 buffer pool、抢占连接池、拖慢上传主链路 |

具体到 turbo-feed，三重困难：

1. **分片键与聚合维度正交**。media 按 `user_id` 分片、comment/report 按 `media_id` 分片——
   「某品类内容近 7 天的完播率」「某用户群体的活跃时段分布」这类查询，无论按哪个键都要广播全部物理表。
   0036 已经实证过广播的代价：仅一个「手机号查重」就从广播全片优化成了单表点查。
2. **join 跨分片键**。行为（comment，media_id 分片）想关联作者（media，user_id 分片），
   任何一层 join 都退化成全分片广播。
3. **行为是持续到达的事件流**。画像要的是「每天增量更新」，不是「偶尔跑一次报表」——
   手写 SQL 聚合连数据源都稳定不起来。

结论：这不是「SQL 怎么写」的问题，是**负载分类**问题。分析负载必须有自己的存储。

## 2. 总架构

```
┌─ OLTP：MySQL 2库×128表（只做事务，结构不动）─────────────────┐
│  user / media / comment / account_credit / outbox_event ...   │
└──────────────┬────────────────────────────────────────────────┘
               │ ① binlog (ROW 格式)
               ▼
        ② CDC 抓取（Canal Server，伪装成 MySQL 从库）
               │  按表拆 topic 的变更事件
               ▼
        ③ RocketMQ（已有集群，削峰 + 可回放）
               │
               ├──→ ④ ClickHouse 明细层（行为事实表 / 内容宽表，ReplacingMergeTree）
               │         │ 物化视图：近1/7/30天聚合
               │         ▼
               │     ⑤ 画像标签（离线 T+1 批算 + 实时增量）
               │         │ 写在线视图
               │         ▼
               │     ⑥ Redis 在线特征（tf:profile:{uid}，复用现有集群）
               │
               └──→ ⑦ 推荐服务 tf-rec（新模块）
                         多路召回 → 粗排 → 精排(先规则后模型) → 重排(去重/多样性)
                         │  正常：候选集打分
                         │  降级：feed-engine 时间倒序（现有读模型原样保留）
                         ▼
                    /api/feed/recommended
```

要点：

- **单向数据流**：OLTP → OLAP 单向出仓。唯一「写回」是画像标签写 Redis 在线特征，
  那是推荐自己的服务存储，不是回写业务库。
- **outbox 与 CDC 并存、不合并**（见 §3.2）。
- **推荐挂了系统不挂**：降级通道就是现在的时间倒序 feed（§5.3）。

## 3. 关键决策与依据

### 3.1 为什么不直接在 MySQL 上聚合（哪怕做了分表）

| 方案 | 结论 | 理由 |
|---|---|---|
| 各分片聚合 + 内存归并 | ❌ 只能当过渡 | 每次查询 fan-out 128 张表；窗口越长扫描越久；连接池 50/库 会被打满，直接挤压上传主链路 |
| MySQL 只读副本上跑分析 | ❌ | 副本仍是行存，聚合语义没变好；只是把拖累隔离了，成本却复制一份 |
| ES 做聚合 | ❌ | 擅长倒排检索与浅聚合，多维滚动窗口聚合与高写入吞吐不是它的主场，且 JVM 堆压力大 |
| **列存 OLAP（ClickHouse）** | ✅ | 列存 + 向量化执行，聚合快 1~2 个数量级；单机即可起步；物化视图天生适合画像标签 |

### 3.2 为什么用 binlog CDC，而不是双写、也不是复用 outbox

| 候选 | 判断 | 关键理由 |
|---|---|---|
| 业务代码双写（写库同时写 CH） | ❌ | 两条写路径必然漂移：任何一方失败就是静默不一致，且**没有对账基准**——两边都是「自己说的」 |
| 复用 outbox 事件 | ❌ | outbox 是**业务语义事件**（时间线投递），只覆盖部分表、粒度粗（一条 media 事件 ≠ 一行变更）；分析层需要的是**全表、行级、可回放**的变更流 |
| **binlog CDC（Canal / Flink CDC）** | ✅ | 业务库零侵入（对代码一行不改）；覆盖全部表（含运营手工修数）；binlog 是单一事实源，天然可对账、可回放重跑 |

⚠️ binlog 前提：`binlog_format=ROW`、`binlog_row_image=FULL`（本地已是 ROW，生产需核查）。

**Canal 还是 Flink CDC？**

| | Canal | Flink CDC |
|---|---|---|
| 形态 | 独立 server，纯投递 | 流计算引擎，抓取+计算一体 |
| 运维 | 单进程，轻 | 需要 Flink 集群（或单机 standalone） |
| 能力 | 投递到 MQ 为止 | 可在管道里做 join / 窗口 / 状态聚合 |
| 结论 | **P1 选它**：需求只是「把变更可靠搬进 MQ」 | **P3 再评估**：等出现「需要流式 join 两张表」的真实需求再上，不要为可能的需求预付复杂度 |

### 3.3 OLAP 选型：为什么是 ClickHouse 起步

| | ClickHouse | StarRocks / Doris | pgvector(PostgreSQL) |
|---|---|---|---|
| 架构 | 单机即可跑（后续可加副本） | 多组件（FE + BE，至少 3 节点才有意义） | 单机 PG |
| 聚合吞吐 | 极高（列存 + 向量化） | 高 | 一般 |
| 多表 join | 弱项（大宽表思路规避） | **强项** | 一般 |
| 物化视图 | 有，画像标签天然工具 | 有 | 无（需手写任务） |
| 运维成本 | 低 | 高 | 最低 |
| 结论 | **P1 起步** | 分析平台化 / 多表 join 需求爆发后再迁 | 只适合 P3 向量检索候选，撑不起画像聚合 |

选型逻辑：**先用最便宜的正确工具，把管道跑通**。CH 的典型玩法是「大宽表 + 物化视图」，
我们正好评价维度可预先 join 进宽表（在 CDC 消费端打宽），绕开它 join 弱的短板。
将来真要交互式多维分析（运营报表），再评估 StarRocks——那是「平台化」阶段的事。

### 3.4 画像分层与标签体系

| 层 | 存储 | 内容 | 更新频率 |
|---|---|---|---|
| 明细层 | ClickHouse | 行为事实表 `user_id, media_id, action(播放/完播/点赞/评论/关注), dwell_ms, ts` + 内容宽表 | 实时（CDC 秒级） |
| 聚合层 | ClickHouse 物化视图 | 近 1/7/30 天窗口：品类偏好 top-k、活跃时段直方图、完播率、互动率 | 分钟级刷新 |
| 服务层 | Redis（现有集群） | `tf:profile:{uid}`：top-k 标签 + 权重 + 版本号，TTL 24h | 由批算/增量任务写入 |

标签三类：

| 类型 | 例子 | 计算方式 |
|---|---|---|
| 静态标签 | 注册渠道、地域、注册时长 | 一次抽取 |
| 统计标签 | 品类偏好 top-5（带权重=加权互动数）、活跃时段、完播率分档、消费深度分档 | 窗口聚合（物化视图） |
| 实时标签 | 最近 20 条互动的内容 id / 作者 id（用于去重与短期兴趣） | CDC 增量直接写 Redis |

⚠️ 冷启动：新用户无行为 → 完全靠注册信息 + 热门兜底；这正好与现有信用分级 L0 观察期语义对齐。

### 3.5 数据规模粗算（为什么这套东西在单机 CH 上毫无压力）

假设目标量级 DAU 10 万、人均 50 个行为事件/日：

| 项 | 估算 |
|---|---|
| 行为事件 | 500 万行/日 ≈ 18 亿行/年 |
| CH 列存压缩后（约 10:1，每行 ~100B 原始） | ~50 GB/年（原始 ~180 GB/年） |
| 单机 CH 承载 | 每秒数十万行写入、画像窗口聚合亚秒返回——**余量巨大** |
| 对分片库的影响 | 零（binlog 拉取是从库级别的 IO，可限速） |

## 4. 与现有系统的关系（不推翻任何已有设计）

| 现有组件 | 在推荐体系中的角色 | 是否改动 |
|---|---|---|
| feed-engine ZSET 池（池1/2/3，时间倒序） | **降级通道** + 召回候选源之一 | 结构不动；`/internal/feed` 接口语义不变 |
| outbox（0037/0040） | 业务事件（审核通过→可见） | 不动，不与 CDC 合并 |
| tf-counter 蓝图（三级计数链路） | **就是 P0**——完播/点赞/播放数据的第一来源 | 按 tf-counter.md 落地即可 |
| AccountStateCache / pub/sub 失效广播 | 画像在线特征同样适用「本地缓存 + 广播失效」手法 | 复用模式 |
| RocketMQ | CDC 事件总线（新增按表 topic，与业务 topic 隔离消费组） | 扩容 topic |
| Redis 集群（3主3从） | 在线特征存储；画像读多写少，注意大 key（top-k 标签控制在 <10KB） | 扩 key 空间 |

## 5. 推荐链路设计

### 5.1 多路召回（每路独立、可开关、可降级）

| 路 | 来源 | 说明 |
|---|---|---|
| 热门 | CH 聚合：时间衰减 + 互动加权分 | 冷启动/兜底主路 |
| 关注关系 | 关注表（OLTP 点查） | 社交分发 |
| 品类/tag 偏好 | Redis 画像 top-k → CH/ES 取候选 | 个性化主路 |
| 同城/地域 | 内容宽表地域列 | 抖音式本地流量池 |
| 向量（P3） | 内容 embedding 相似检索 | 语义泛化 |

### 5.2 排序与重排

- **P2 用规则打分**：`score = w1·热度 + w2·偏好匹配度 + w3·新鲜度衰减 + w4·作者多样性与已曝光惩罚`，
  权重进配置，可灰度可回滚——**先让链路跑起来、能对比，再谈模型**。
- **P3 再上模型**：LR → GBDT（特征就是 §3.4 的标签 + 内容统计），训练样本由 CH 明细层直接出。
- 重排：已曝光过滤（Redis set / 布隆，key 按 uid+日期分桶）+ 同作者/同品类打散。

### 5.3 降级路径（本设计最值钱的稳定性决策）

```
推荐服务可用   → 召回+重排结果
推荐服务不可用 / 特征缺失 / 超时(如 >80ms) → 退回 feed-engine 时间倒序（现状）
```

feed-engine 的读模型**原样保留**，推荐层是叠加而不是替换。任何时候关闭 tf-rec，
系统退回今天的形态——上线风险被结构性消解。

## 6. 分期落地

| 期 | 内容 | 新组件 | 验收标准（能回答的业务问题） |
|---|---|---|---|
| **P0**（零新组件） | 落地 tf-counter（播放/点赞/完播三级计数）+ 热门分推荐（时间衰减+互动加权） | 无 | 「热门流和纯时间倒序相比，互动率有差异吗？」 |
| **P1** | Canal → RocketMQ（按表 topic）→ CH 明细层 + T+1 离线标签批算 | Canal、ClickHouse | 「能查到任意用户的 top-5 品类偏好与活跃时段吗？」 |
| **P2** | 实时标签（物化视图分钟级）+ 多路召回 + 规则重排接入 feed-engine（带降级） | 无（复用） | 「个性化流的曝光→互动转化率高于热门流吗？」（A/B） |
| **P3** | 向量召回 + 排序模型 +（视需求）Flink 流式管道 | 向量库、可选 Flink | 「模型排序相对规则排序的提升是多少？」 |

向量库到时候再选（Redis 8 vector set / pgvector / Milvus / Qdrant 对比），现在不决策。

## 7. 明确不做的事（与做什么同样重要）

1. **不在分片库上为分析加索引/加宽表**——分析负载一律出仓。
2. **不做业务双写**——binlog 是唯一事实源。
3. **不合并 outbox 与 CDC**——业务事件与数据出仓职责不同、SLA 不同、消费者不同。
4. **P3 之前不引入 Flink / K8s / 多机房**——单机 CH + Canal + 已有 MQ 足以支撑到 P2 的目标量级。
5. **不做实时强一致画像**——画像秒级~分钟级新鲜度足够；一致性靠「降级到时间倒序」兜底。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| binlog 延迟/断流 → 画像过期 | 消费延迟监控 + 按表位点对账任务（对比 CH 行数 vs 业务库 COUNT）；CH 侧数据可全量重放（binlog 可回放） |
| CH 单机无 HA | **接受**：分析层挂掉 → 推荐自动降级时间倒序，线上不受影响；CH 重启后从 MQ 位点续传 |
| 画像大 key 拖垮 Redis | top-k 标签上限（<10KB）+ 版本号整体覆盖写 + 走独立 db |
| 合规 | 画像最小化（不存明文敏感属性）、支持按用户删除（CH ALTER DELETE + Redis 删 key） |
| 过度设计 | 每期有独立验收与 A/B；上一期没跑出收益，下一期不启动 |
