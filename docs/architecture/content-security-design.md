## 1. 为什么要重构：三条实测缺口

改造前的形态是「各业务自己调 `sensitiveWordService.requireClean(text)`」。审查时实测出：

| # | 现象 | 实测证据 | 后果 |
|---|---|---|---|
| 1 | 机审关键词永不命中 | `RuleBasedModeration.banned-keywords` 匹配的是对象名末段，而对象名由服务端拼成 `{keyPrefix}/{uid}/{uuid}.{ext}` | 配置里那 4 个词**完全没在干活** |
| 2 | 词库为空 | `SELECT COUNT(*) FROM sensitive_word` = 0 | `requireClean` 等价于「什么都不做」 |
| 3 | 没有任何出口能暴露 1、2 | 无指标、无 health、无启动告警；接口全 200 | **静默失效** |

**结论：最大的问题不是"拦不住"，而是"拦不住这件事没人知道"。** 一个词库为空的过滤器，
从启动日志、从接口响应、从任何角度看都"正常"。因此 S1 的**第一优先级是让失效可见**，
而不是先去堆匹配算法。

附带缺口：`nickname` 完全未过滤且无长度上限、`caption` 无长度校验（列宽 2048，超限抛
SQL 异常表现为 500）、词条 `category` 被丢弃无法分级、命中无留痕无指标。

## 2. 架构：五层（职责边界比算法更重要）

```
   写路径调用方（注册 / 上传 / 评论 / 改描述）
        │
   ① 接入层  ContentSecurityService#requireClean(scene, text, userId)
        │      · 长度校验（最便宜的检查放最前）
        │      · 返回 ContentVerdict；不合格抛 BizException
        ▼
   ② 预处理层 TextNormalizer：NFKC → 剥不可见 → 剥分隔符 → 小写 → 繁简
        │      · 输出「归一化下标 → 原始下标」映射，供高亮回溯
        ▼
   ③ 匹配层  AhoCorasick（不可变快照 + 原子引用热切换）
        │      · 只认字面，不做决策；返回 SensitiveWordHit（词 + 分类 + 位置）
        ▼
   ④ 决策层  白名单 → 分类 → 动作表
        │      · PASS / LIMIT（降权）/ REVIEW（转人审）/ BLOCK
        ▼
   ⑤ 处置与反馈 计数（LongAdder）+ 结构化日志 + stats 快照
```

| 层 | 类 | **不**在本层做的事 |
|---|---|---|
| ① | `ContentSecurityService` | 不做匹配、不直接读库 |
| ② | `TextNormalizer` | 不判断敏不敏感（纯函数、无状态） |
| ③ | `AhoCorasick` / `SensitiveWordService` | **不抛业务异常**、不看白名单 |
| ④ | `WhitelistService` + `ContentSecurityProperties` | 不扫文本 |
| ⑤ | 计数与日志 | 不参与拦截判定 |

> **为什么要把"匹配"和"决策"拆开**：改造前 `requireClean(text)` 同时承担匹配与拒绝，
> 于是每个调用方都绑死在「命中即拒」这一种策略上。想给评论换策略（转人审而非拒）就得改所有调用点。
> 拆开后策略调整只动 ④ 一处。

## 3. 契约层

| 类型 | 作用 | 关键设计 |
|---|---|---|
| `ContentScene` | `NICKNAME` / `CAPTION` / `COMMENT` | 不同位置合规尺度不同；不分场景只能取最严一刀切 → 正常评论被大量误杀 |
| `ModerationAction` | `PASS` / `LIMIT` / `REVIEW` / `BLOCK` | **诚实标注当前强制程度**：`REVIEW` 现等价 `BLOCK`、`LIMIT` 现等价 `PASS`。不假装它们已接通 |
| `ContentVerdict` | 动作 + 场景 + 命中词 + 分类 + 是否豁免 + 原文命中区间 | 一次性返回调用方/运营/排障三方的全部需要；只返回布尔值就只剩日志 |
| `SensitiveWordHit` | 词 + 分类 + 命中位置 | 位置在扫描时是顺手可得的，事后 `indexOf` 反查会指错（同词多次出现时） |

> 契约类字段**不带 `get`/`is` 前缀**：Jackson 会把它们当属性序列化进 JSON
> （本项目在 `FeedTimelineEvent` 与 `Result#isSuccess` 上踩过两次）。

## 4. ② 预处理：归一化流水线（抗绕过的主战场）

```
① NFKC 折叠（Ａ→A、①→1、㈱→(株)）
② 剥离不可见字符（零宽/方向标记/BOM/软连字符）—— 恒开，无开关
③ 剥离分隔符（非字母数字）—— 开关控制
④ 小写折叠
⑤ 常用繁体 → 简体 —— 开关控制
```

**顺序不能换**：① 必须在 ③ 之前。曾经写反过 —— 先按「非字母数字即分隔符」剔除时，
`㈱` 这类符号类兼容字符会被直接删掉，NFKC 的展开分支**永远走不到**，而单看输出
「文本变短了」发现不了。

| 变体 | 输入 | 归一化 | 是否拦住 |
|---|---|---|---|
| 原形 | `测试敏感词` | `测试敏感词` | ✅ |
| 分隔符穿插 | `测 试-敏 感词` | `测试敏感词` | ✅ |
| 繁体 + 穿插 | `測 試 敏 感 詞` | `测试敏感词` | ✅ |
| 零宽字符 | `测\u200b试\u200b敏\u200b感\u200b词` | `测试敏感词` | ✅ |
| 繁体 | `賭博` | `赌博` | ✅ |
| 全角 + 大写 | `ＡＢＣ` | `abc` | ✅ |

**③ 是误杀率最高、收益也最高的一步**：剥掉分隔符后「顺 丰 车」可能被拼成敏感词。
这是刻意接受的代价，出口是**白名单** —— 必须先有白名单再开这一步。

**下标回溯**：归一化会改变长度，只返回文本则命中下标落不回原文（前端高亮错位）。
实测 `测 试-敏 感词`（8 字符）归一化后命中 `[0,5)`，回溯原文得 `[0,8)` —— 正确覆盖被剥掉的
分隔符区间。

**繁简映射表（637 条）带两道自检**：
- **编码自检**：每条必须是 2 个相异字符。历史事故是用一条长字符串编码，手滑漏写一个字导致
  后面所有条目**整体错位且静默运行**，只在匹配时才暴露。
- **方向自检**：对 80 个高频繁简体对做「繁→简」断言。若写反（简→繁），简体文本会被转成繁体，
  **所有简体词条全部漏放** —— 灾难级且极难靠观察发现。

> 覆盖面是**常用字表，不是完整 OpenCC**。未收录的生僻繁体仍可绕过，属已知边界；
> 完整方案需引入第三方数据文件，与「零三方依赖」定位冲突，需单独批准。

## 5. ③ 匹配层：基准数据决定了"不要做什么"

AC 自动机（HashMap 子节点，不可变 + 原子引用整体替换 + 零锁读）。实测（50 字文档、单线程）：

| 词库规模 | 单次扫描 | 吞吐 | 内存 | 全量构建 |
|---|---|---|---|---|
| 1k | 0.29µs | 3.47M QPS | 10MB | — |
| 10k | 0.48µs | 2.10M QPS | 17MB | — |
| 200k | 1.36µs | 738K QPS | 127MB | — |
| 1M | 2.76µs | 362K QPS | 590MB | 1.2s |

最坏用例（深状态且全程不命中）约 30µs，相对常态退化 11~64 倍。

**结论（反直觉，由数据决定而不是照搬大厂）**：吞吐**不是**本项目瓶颈。真瓶颈是
① 每次全量重建的延迟（1M 词 1.2s 会卡住写请求）② 内存 ③ 静默失效。
因此**不引入 DAT / 分片词库 / 分布式词库服务** —— 那是为千万词级词库 + 百万 QPS +
成规模运营团队设计的。升级顺序：**先让失效可见 → 再增量更新 → 最后才动内存结构**。

> 基准脚本的教训（写微基准时）："最坏用例"必须**验证它真的触发了退化**。
> 第一版的后缀词库（测、测测…）因首字符即命中而短路，测出"更快"的假结论。

## 6. ④ 决策层：白名单与分级动作

### 白名单（误杀治理的唯一出口）

任何词库都必然误杀。没有豁免出口时运营只能二选一：删词（漏放）或留着（误杀）。
白名单把「是否敏感」从**词的属性**改成**词 × 场景 × 主体**的属性：

- **场景**：`*` / `NICKNAME` / `CAPTION` / `COMMENT` —— 同一个词在评论里放行、在昵称里仍拦
- **主体**：`GLOBAL`（对所有人）/ `USER`（仅 `owner_id` 本人，个案申诉用，不放开全站）

白名单**只做减法**（命中→放行），**不做加法**（不会让未命中的文本被拦截），
所以误配的最坏结果是漏放而非新误杀 —— 这让它可以安全地开放给运营自助维护。
被豁免的命中**仍然留痕**（`ContentVerdict.whitelisted=true` 且保留 `matchedWord`），
用于统计「哪些词命中最多却总被豁免」—— 那正是词库该收敛的信号。

### 分级动作

`category-actions` 默认留空 → 所有分类统一走 `default-action: BLOCK`（与改造前行为一致）。
运营明确策略后再逐条配置（如 `AD: LIMIT`）。

`REVIEW` / `LIMIT` 当前分别等价 `BLOCK` / `PASS`（审核队列与 feed 降权尚未接通），
代码与文档**都显式标注**，避免运维按「REVIEW 会进人审队列」的预期配置、实际却把内容直接拒了。

### 失败方向

整条链路 fail-closed（命中即拒）；白名单是唯一的 fail-open 环节，且方向是只减不增。

## 7. 数据模型

| 表 | 位置 | 要点 |
|---|---|---|
| `sensitive_word` | `ds_0`（turbo_feed_1） | 词库；变更检测用 `(COUNT, MAX(updated_at))` 指纹 |
| `sensitive_whitelist` | `ds_0`（turbo_feed_1） | **本次新增**；`(word, scene, scope, owner_id)` 唯一键 |

⚠️ **两张表都必须在 `shardingsphere-config.yaml`（及 `-128.yaml`）的 `!SINGLE` 里登记**
（`tables: [ds_0.表名]`，元素必须「数据源.表名」全限定）。ShardingSphere 5.5.3 **不会**
把未纳入规则的表放进逻辑元数据，漏登记的症状是启动即抛 `TableNotFoundException`
—— 本次验证就踩了一次（改了配置但没同步到运行期 classpath，见 changelog 0028 的排障记录）。

⚠️ **排序规则刻意不同**：`sensitive_word` 沿用库级 `utf8mb4_0900_ai_ci`（大小写/重音不敏感，
已实测出「加 Abc 后再加 abc 不新增行、文本里的 abc 却拦不到」的坑）；
新建的 `sensitive_whitelist` 显式 `COLLATE utf8mb4_bin`（精确匹配），
因为白名单是**精确豁免**语义，必须与 AC 的逐字符匹配一致，否则会意外豁免掉 `ABC`。

热更新：两表同源 —— 启动加载 + 30s 指纹检测 + admin 写操作立即刷新，
不可变快照 + `AtomicReference` 整体切换（AC 与「词→分类」映射必须在**同一个**原子引用里切换，
否则存在「新词命中了但按旧分类处置」的窗口）。

## 8. 配置（`turbofeed.content-security.*`）

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关，用于「怀疑误杀」时快速回滚 |
| `fail-startup-on-empty-dictionary` | `${TURBOFEED_FAIL_ON_EMPTY_DICT:false}` | **生产应置 true**，把「忘了导词库」挡在部署阶段 |
| `scene-max-length` | NICKNAME 32 / CAPTION 2048 / COMMENT 1024 | 与 DB 列宽、前端上限同一事实源 |
| `max-text-length` | 4096 | 兜底上限，同时限制 AC 扫描成本 |
| `normalize.*` | enabled/strip-separators/fold-traditional 均 `true` | 抗绕过 |
| `whitelist-enabled` | `true` | 误杀出口 |
| `category-actions` / `default-action` | `{}` / `BLOCK` | 分级策略 |

> 本段**刻意不含任何具体词条**：词条是运营数据（库表 + admin 接口），
> 把词写进默认配置等于让「克隆即跑」自带一份不该公开的名单。
> （既有的 `media.review.banned-keywords` 里的 4 个 demo 词属同类问题，见 §11 遗留。）

## 9. S1 的核心产物：让「有没有在工作」一次调用可回答

| 手段 | 内容 |
|---|---|
| 启动自检 `ContentSecurityService#verifyDictionary` | 词库为空 → 按开关拒绝启动或 WARN；非空 → INFO 输出词库/白名单/归一化开关/**繁简映射 637 条(非法=0, 方向自检失败=0)** |
| 结构化日志 | 未通过：`scene / action / word / category / userId / hit=[start,end)`；豁免：`敏感词命中但被白名单豁免` |
| 计数器 | `场景:结果` → LongAdder 累计（含 `WHITELISTED` 单独一档） |
| `stats()` 快照 | 开关、词库大小、DB 行数、白名单大小、归一化开关、映射自检、计数 |

**为什么计数比想象中重要**：命中恒为 0 且词库非空 = 可能全被绕过；豁免数远超命中数 = 白名单配得太宽。
改造前这两类信号一个都没有。

实测启动日志：
```
内容安全启动自检通过: dictionarySize=3, whitelistSize=1, normalize=on(strip开 / trad开),
  繁简映射=637条(非法=0, 方向自检失败=0), 默认动作=BLOCK
```

## 11. 已知边界与遗留

1. **图片视觉审核仍缺失**：文本拦得再严也管不住图。整套审核的"拦不住"根因仍在，
   需机器初审（云 API 或本地视觉模型），见 [moderation-design.md](moderation-design.md)。
2. `media.review.banned-keywords` 的 4 个 demo 词仍写在默认配置里（违反「demo 值不进仓库配置」约束），
   且因匹配对象名而永不命中 —— 建议删除或改匹配文案，需单独确认。
3. 繁简映射只覆盖常用字表（637 条），非完整 OpenCC。
4. **白名单与词库都只有"即时刷新"当前实例**：多实例下最长滞后 30s（定时指纹兜底）。
5. `sensitive_word` 的 `uk_word` 仍是 `utf8mb4_0900_ai_ci`（大小写不敏感），
   修它会影响存量数据，属行为变更，未动。
6. 昵称目前只在注册时检测；若日后开放"改昵称"入口，必须同样走统一入口。
7. 计数是进程内累计（重启归零），未接入 micrometer/health 端点。

## 12. 路线：S2 / S3 / S4（⏳ 规划，未实现）

| 阶段 | 主题 | 事项 |
|---|---|---|
| **S2** | 增强抗绕过 | 拼音/谐音折叠、拆字变形、重复字符压缩、emoji 语义；变体命中率专项基准 |
| **S3** | 可运营 | 命中留痕表（词/场景/分类/用户/时间）、审核工作台对接、误杀率与漏放率看板、灰度词（先标记不拦截） |
| **S4** | 能力升级 | 词库增量更新（按 revision 范围拉取，消除 1.2s 全量重建卡顿）、大词库内存结构优化、多实例刷新一致性（广播/版本号） |

### 明确不做（过设计清单）

- 不引入 DAT / 分片词库 / 分布式词库服务 —— 吞吐不是瓶颈（§5 数据）
- 不引入完整 OpenCC 依赖 —— 与「零三方依赖」冲突，需单独批准（§4）
- 不做"全量命中收集" —— 写路径一旦命中即拒，求全只增加开销
- 不做客户端侧过滤 —— 可被绕过，只做服务端
- 不做实时模型推理 —— 属于机器初审（视觉）范畴，另开专题
