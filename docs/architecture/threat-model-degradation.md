# 威胁模型与降级矩阵（认证 / 鉴权）

> **状态：生效（M0 落地）**
> **定位**：本文件是安全降级策略的**唯一登记处**。代码中任何「依赖不可用怎么办」的分支，都必须能在 §3 矩阵里找到对应一格。
> **范围**：tf-gateway 认证链路（JWT 签发/校验、令牌黑名单、刷新令牌）与网关 ↔ 引擎服务间鉴权。

---

## 1. 为什么需要这张表

整改前，`TokenBlacklist#isRevoked` 在 `catch` 里直接 `return false`（fail-open），理由写在 Javadoc 里。
这是一种**隐式二选一**，有三个具体问题：

| 问题 | 后果 |
|---|---|
| 无法通过配置判断当前模式 | 只能读源码才知道"Redis 挂了会放行" |
| 降级不可观测 | 请求照常 200，日志只有一行被滚动淹没的 warn，监控无指标 |
| 无法在故障期间切换 | 想改成拒绝只能改代码重新发版 |

M0 的判定标准：**任何"中间件不可用时的兜底分支"必须满足其一**——

1. **fail-closed**：拒绝请求（安全优先）；或
2. **fail-open**：放行，但必须带**显式配置开关 + 每次降级可观测**（日志 + 指标 + 登记进本矩阵）。

---

## 2. 威胁模型（三个场景）

| # | 场景 | 保护的资产 | 主要威胁 | 防护手段 | 残余风险 |
|---|---|---|---|---|---|
| S1 | **JWT 签发 / 校验** | 用户身份（`uid` + `role`），管理端权限 | ① 密钥泄露 → 伪造任意 uid / role=ADMIN 的令牌；② 令牌被篡改 / 过期仍被接受 | HS256 验签（常量时间比较）；密钥无默认值、缺失即启动失败（`JwtProperties`）；`jti` + `type` 声明，刷新令牌不得当访问令牌用 | 纯无状态令牌在 exp 之前无法被动失效 —— 由 S2 补齐 |
| S2 | **JWT 黑名单（吊销）** | 「登出 / 风控踢人 / 盗号止损」的可执行性 | Redis 不可用时，已吊销令牌被放行，止损失效且**完全不可见** | 验签后二次查 `turbofeed:jwt:blacklist:{jti}`；TTL = 令牌剩余有效期（自清理，无需 GC）；**默认 fail-closed**，开关切 fail-open 时留下指标 | fail-closed 下 Redis 抖动会放大为 401（可用性代价，已在 §3 记录取舍） |
| S3 | **服务间内部鉴权** | `/internal/**` 接口（流量池晋级回调、计数投递等） | 内网任意调用方 / 端口暴露时直打内部接口 | 网关与引擎两侧 `InternalTokenInterceptor` 校验 `X-Internal-Token`；**缺令牌仅 dev/local 允许放行** | dev/local 环境仍无鉴权（可接受：本地开发，且启动有 banner 告警） |

## 3. 降级矩阵（核心）

### 3.1 S1 JWT 签发 / 校验 —— 无中间件依赖，**无降级分支**

| 依赖 | 故障情形 | 行为 | 开关 | 可观测性 | 后果 |
|---|---|---|---|---|---|
| JWT 密钥（配置项） | 未注入 / 长度 < 32 | **启动失败**（`JwtProperties` + `application.yml` 双保险） | 无（刻意不提供兜底） | 启动日志 | 进程起不来，运维立刻可见 |
| — | 令牌过期 / 签名不符 / 类型非 access | 401 `40101` | 无 | 业务错误码 | 请求被拒，客户端重新登录 |
| — | 令牌无 `jti`（旧格式） | 验签通过但**无法单点吊销**，按策略拒绝 | 无 | — | 见 `JwtUtil#parseForRevoke` |

> S1 不需要降级策略：它不依赖任何中间件，"失败"只有一种形态——请求不合法，直接拒绝。

### 3.2 S2 令牌黑名单 —— 依赖 Redis，**默认 fail-closed**

| 依赖 | 故障情形 | 当前行为 | 开关 / 配置 | 可观测性 | 后果 | 何时切换 |
|---|---|---|---|---|---|---|
| Redis | `hasKey` 抛异常 | **按"已吊销"处理 → 拒绝请求（fail-closed）** | `turbofeed.security.token-blacklist-fail-open-on-error: false`（**默认**） | 指标 `turbofeed.security.blacklist.error{mode="closed"}`；ERROR 日志（每 50 条打 1 条，防日志风暴） | Redis 故障期间全部带令牌请求 401 | Redis 长时间故障且业务上宁可承担"已登出令牌仍可用" |
| Redis | `hasKey` 抛异常 | 按"未吊销"处理 → 放行（fail-open） | 开关置 `true` | 指标 `...error{mode="open"}`；WARN 日志（同样节流） | 已登出 / 已风控的令牌在故障期间仍可用（**安全代价，但可见**） | 故障恢复后**必须**改回 false |
| Redis | 吊销**写入**失败 | 不抛异常（登出接口仍返回成功），但记为 ERROR/WARN | 同上开关决定日志级别 | 指标 `...error{mode="write"}` | 用户点了登出，令牌却仍可用 | — |

**为什么默认 fail-closed**：

- 黑名单存在的唯一目的就是「登出 / 风控踢人 / 盗号止损」。在 Redis 抖动期间放行，等于把安全闸口在**最需要它的时候**关掉，而且这种放行在日志和监控上完全不可见（请求照常 200）。
- Redis 在本项目已是强依赖（限流、时间线、计数器、热点缓存），因此默认 fail-closed **不会显著放大故障面**。
- 最坏情况退化为"全站 401"，是**可感知、可告警、可切换**的失败；而 fail-open 的最坏情况是"盗号止损失效"，是**静默**的失败。

**为什么不把写入失败也改成抛异常**：登出是用户主动操作，客户端通常不处理响应，抛异常既不会带来重试，还会让"Redis 挂了连登出都报错"；但失败必须**可见**——因此按模式打 ERROR/WARN 并累加 `mode="write"` 指标，而不是静默吞掉。

### 3.3 S3 服务间内部鉴权 —— 依赖配置，**缺令牌即启动失败**

| 依赖 | 故障情形 | 行为 | 开关 / 配置 | 可观测性 | 后果 |
|---|---|---|---|---|---|
| 配置 | 缺令牌 + `dev`/`local` profile | 放行（fail-open，保证「克隆即跑」） | `--spring.profiles.active=dev\|local` | **启动 banner 大字告警** | 本地开发无鉴权，可接受 |
| 配置 | 缺令牌 + **其它任何 profile**（含无 profile 的 default、staging、prod） | **启动抛 `IllegalStateException`** | 无 | 启动失败日志 | 进程起不来，运维立刻可见 |
| 配置 | 令牌存在但不匹配 | 401（网关 `40101`；引擎直接写 401 + JSON） | 无 | — | 请求被拒 |
| compose | 宿主未设 `TURBOFEED_INTERNAL_TOKEN` | `docker compose` **直接报错退出**（不静默传空串） | `${TURBOFEED_INTERNAL_TOKEN:?...}` | compose 错误信息 | 部署前置拦截 |

**为什么从"仅 prod fail-closed"收紧为"非 dev/local 即失败"**：内部接口裸奔的判定成本在运行期几乎为零（日志看不到、监控不报警），某个中间环境一旦漏配就**永久静默**。把 fail-open 收敛成显式白名单后，漏配立刻变成"起不来"。

### 3.4 同族组件（登记备查，不改变现状）

| 组件 | 依赖 | 故障行为 | 模式 | 说明 |
|---|---|---|---|---|
| `RefreshTokenStore` | Redis | store / revoke 尽力而为、仅记日志；RT 校验失败 → 401 | fail-open | 刷新令牌失败只是让用户重新登录，属可接受代价；此处**刻意**与黑名单区分开：黑名单管"止损"（不可放行），RT 管"续期"（放行的代价仅是体验） |

## 4. 切换 Runbook（S2）

1. 确认 Redis 故障：`turbofeed.security.blacklist.error` 指标持续上涨，或 `/actuator/health` 中 Redis DOWN。
2. 临时降级：置 `TURBOFEED_SECURITY_TOKEN_BLACKLIST_FAIL_OPEN_ON_ERROR=true` 并滚动重启网关。
3. 观察：指标应从 `mode="closed"` 转为 `mode="open"`，WARN 日志出现。
4. 恢复：Redis 恢复后**必须**改回 `false` 并重启 —— 否则"登出即失效"这条保证长期失效，且无人察觉。
5. 复盘：记录故障期间有多少请求处于 fail-open（指标差值）。

---

## 5. 变更纪律

改动任一格子的代码时，**必须同步三处**，缺一不可：

1. 本文件对应格子（行为 / 开关 / 指标 / 后果）；
2. `application.yml` 中该开关的注释（说明两种取值与后果）；
3. 对应单测（当前：`InternalTokenInterceptorTest`（双端）、`TokenBlacklistTest`）。

**新增任何"依赖不可用兜底分支"时**：先来本表登记，再写代码。若无法归入 fail-closed / 显式 fail-open 之一，说明设计有问题，需要重新讨论而不是先落地。
