# 审核体系设计蓝图（P0~P3）

> **本文性质：设计蓝图，不是现状描述。** 正文中除标注 **✅ 已实施** 的条目外，
> 其余均为**规划中未实施**，用于对齐演进方向与验收标准；请勿据本文认为某项能力已具备。
> 现状以 `docs/modules/tf-gateway.md` §4 与代码为准。
>
> 对标对象：抖音式「机器初审 → 分级处置 → 人工复审 → 申诉兜底」审核链路。

## 0. 现状盘点

### 0.1 已具备（含代码坐标）

| 环节 | 实现 | 落点 |
|---|---|---|
| 文本机审 | Aho-Corasick 敏感词，精确子串匹配，命中即 `BizException`（fail-closed） | `SensitiveWordService#requireClean`，服务于 media caption（3 处）与 comment |

| 机审可插拔 | 按 `moderation-mode` 选实现，主流程零改动 | `ContentModeration` / `ContentModerationRouter` / `ModerationMode` |
| 信用分级分流 | L0 先审后放 / L1·L2 先发后审，初始流量池由等级决定 | `CreditLevel`（`poolLevel`：L0=0 / L1=1 / L2=3） |
| 新人观察期 | 新号默认 L0 口径，人审通过达阈值转正 | ✅ 已实施，见 `docs/changelog/0027` |
| 状态机 | `CAS + 有界重试`，`transitioned` 区分「结果状态」与「是否我流转」 | `MediaReviewService#review` |
| 举报 / 申诉 | 高危举报即时下架停推；普通举报入人审队列；申诉中间态 | `report` / `appeal` 表 + `MediaReviewService` |

### 0.2 空缺（按影响排序）

| 缺口 | 后果 |
|---|---|
| **图片内容无真实识别** | 涉黄/暴恐/涉政图片**完全依赖人工**；机审形同虚设 |
| **机审只有二值输出** | 无「疑似」档，无法把中等把握流量送人审并限流 |
| **文本匹配无变体归一化** | 谐音 / 拼音 / 全半角 / 穿插符号 / 简繁即可绕过词库 |
| **无审核审计表** | 谁在何时因何裁定不可追溯，申诉与复盘无据 |
| **队列无优先级** | 高风险内容与普通内容同队同速，人审算力平摊 |
| **无 SLA 与一致性监控** | 队列积压、审核员口径漂移不可观测 |
| **流量池发布即定，无动态晋升** | 好内容缺少「跑起来」通道，坏内容只靠事后下架 |
| **机审加载失败为软失败** | 启动期词库加载异常仅留一行 ERROR + 空 Trie → **全部文本放行**（`0026` 遗留） |

### 0.3 与抖音的差距对照

| 能力层 | 抖音 | turbo-feed 现状 | 差距 |
|---|---|---|---|
| 机器初审 | 视觉 + OCR + ASR + 文本多模态，输出置信度 | 文件名级规则 + 文本精确词表 | **一个数量级** |
| 分级处置 | 确定违规 / 疑似 / 通过 → 拦 / 限流+人审 / 放行 | 二值：拦 / 放 | 结构性缺失 |
| 人工复审 | 分优先级队列 + SLA + 双人复核 + 抽检 | 单一时间序队列 | 运营能力缺失 |
| 申诉兜底 | 独立申诉链路 + 误判回流模型 | 有申诉状态机，无回流 | 半闭环 |
| 分发联动 | 审核结论直接联动推荐流量池 | 发布时定池，无动态调整 | 半联动 |

**机制骨架（分级分流 / 状态机 / 申诉 / 信用底盘）与抖音同构，缺的是「能力深度」——机审深度、运营工具、数据闭环。**

## 2. P0：优先补齐（安全收益最直接）

### P0-1 机审置信度分级

**问题**：`ContentModeration#moderate` 返回 `MediaStatus`（APPROVED / REJECTED），二值结构下**没有「中等把握」的表达位置**。要么放行要么拦截，逼实现方在两端压注：放宽 → 漏放；收紧 → 误杀。

**方案**：把端口返回改成「裁定 + 置信度 + 标签」，二值降级为其特例。

```java
public record ModerationVerdict(
        MediaStatus decision,      // 二值结论（保持既有下游契约）
        double confidence,         // 0~1
        List<String> labels,       // 命中标签，如 porno / politics / ad
        boolean needHumanScan) {}  // 是否强制送人审
```

- `ContentModeration` 增加 `default ModerationVerdict verdict(...)`，默认委托 `moderate()` 并给 `confidence=1.0`；
  **既有实现零改动**，新实现按需覆盖（避免一次性大改所有实现类）。
- `MediaReviewService` 按 verdict 分流：`REJECTED` → 拦；`needHumanScan || confidence < 阈值` → 强制 L0 口径入队（**不论信用等级**）；否则走现有信用分级。
- 新增配置 `turbofeed.media.review.confidence-threshold`（默认 0.9）。

**验收**：构造 `confidence=0.7` 的假机审实现 → 高信用（L2）账号内容也进人审队列，且不进公域；
`confidence=0.99` 通过 → 维持原有信用分级行为。

**风险**：新增 `needHumanScan` 会让 L2 流量也进人审，**人审量可能显著上升** → 需与 P1-2（队列优先级）、P1-3（SLA）配套，否则队列先崩。

### P0-2 文本变体归一化

**问题**：`AhoCorasick` 是**精确子串**匹配，`requireClean` 直接喂原始文本。以下均可绕过：
全角（`涉　黄`）、零宽字符插入、标点穿插（`涉-黄`）、大小写（对英文词）、繁体（`賭博`）、拼音/首字母（`seqing` / `sq`）、谐音（`色情`→`涩情`）。

**方案**：在 `requireClean` 前加**归一化流水线**，把变体折叠回规范形再匹配：

```
原始文本
 → Unicode NFKC（折叠全角/兼容字符）
 → 去零宽与不可见字符（U+200B~U+200F、U+FEFF…）
 → 去分隔符（非字母数字汉字一律剔除，抗"插-入-符-号"）
 → 大小写归一
 → 简繁统一（OpenCC 或内置常用映射表）
 → 拼音/首字母映射（可选，误杀率最高的一步，建议默认关）
 → 送 Aho-Corasick
```

配套：命中后**回溯原始文本位置**给出准确高亮（归一化会改变下标，需维护「归一化坐标 → 原文坐标」映射，否则前端高亮错位）。

**验收**：对同一条违禁词的 7 类变体（全角/零宽/穿插/繁体/大小写/拼音/谐音）逐一构造用例，
归一化后全部命中；同时对 20 条正常文本（含「代开发票」类易误杀样本）零误杀。

**风险**：**误杀率上升是必然的**（去掉分隔符后「顺丰车」类正常词可能拼出敏感词）→
必须配**白名单**机制（精确放行词，优先级高于词库），并给词库加 `match_mode`（精确/归一化）分级，
高误杀风险词只走精确匹配。

### P0-3 机审加载失败改为启动显式失败

**问题**（`0026` 遗留）：`SensitiveWordService` 的 `@PostConstruct` 把加载异常 catch 住、保留空 Trie，
**所有文本放行**——fail-closed 设计静默失效，日志里只有一行 ERROR，运维极易漏判。

**方案**：区分两类失败并给出不同处置：

| 失败类型 | 处置 |
|---|---|
| 建表/路由类错误（配置问题，重试无意义） | **启动直接失败**（与 `SnowflakeConfig#requireInstanceId` 同风格） |
| 词库查询失败（DB 抖动） | 有界重试；仍失败则**置「未就绪」标志**，`requireClean` 在未就绪时 **fail-closed 拒绝全部写入**（宁可挡住，不可放过），并暴露健康指标 |

**验收**：人为把 `sensitive_word` 表改名 → 应用**启动失败并给出明确原因**；
人为在运行期断开 DB 后建表查询失败 → 写入接口返回明确错误码，不静默放行。

## 3. P1：运营能力（人审从「能审」到「审得动」）

### P1-1 审核审计表 `review_log`

**问题**：状态流转目前只进应用日志（`log.info("审核状态流转（整帖）…")`），**不可查询、不可追溯**。
申诉时无法回答「谁在何时因何驳回」。

**方案**：新增 `review_log` 表。**分片键选 `media_id`**——与 `report` / `appeal` 同维度，
「查某条内容的全量审核轨迹」单分片命中，与既有分片设计一致（见 `docs/architecture/sharding.md`）。

| 列 | 说明 |
|---|---|
| `id` / `media_id` | 主键（雪花）/ 分片键 |
| `action` | `MACHINE_PASS` / `MACHINE_REJECT` / `HUMAN_APPROVE` / `HUMAN_REJECT` / `TAKEN_DOWN` / `APPEAL_UPHELD` |
| `from_status` / `to_status` | 流转前后状态 |
| `operator_id` | 机审为 NULL，人审为管理员 userId |
| `reason_code` / `reason_text` | 结构化理由码 + 备注 |
| `extra` | JSON：机审置信度、命中标签、举报单号 |
| `created_at` | 时间 |

**实现要点**：写入点放在 **CAS 成功之后**（`rows > 0` 才写），落在同一事务内。
`autoTables` 新增逻辑表时**必须同步在 `shardingsphere-config.yaml` 登记**——
未纳入 `!SHARDING` 的表需显式加 `!SINGLE`，否则 `TableNotFoundException`（`0026` 教训）。

**验收**：一条内容完整走完「机审→人审驳回→申诉→翻案」，`review_log` 恰好 5 行且时序正确。

**风险**：日志表增长速度 ≈ 审核次数，需配套归档（按月分区或历史表）。

### P1-2 人审队列优先级

**问题**：队列是 `PENDING` 按时间序，**高风险内容与普通内容同速**。生态风险高的内容（举报关联、
新人/低信用、时效性内容）被人审算力平摊拖慢。

**方案**：队列排序键 = 加权得分，而非单一时间：

```
priority = 举报关联权重(↑)
         + 信用等级权重（L0 高于 L1）
         + 等待时长（防饿死，随时间线性增长）
         + 内容类型权重（可选：直播/时效内容优先）
```

- 低复杂度落点：在 `media` 上加 `review_priority` 列，查询 `ORDER BY review_priority DESC, created_at`；
- 高吞吐落点：Redis ZSET 优先级队列（`ZADD` score=priority），DB 兜底与重建；
- **必须带「等待时长增长项」**，否则低权重内容永久饥饿。

**前置**：P1-1（优先级的输入里含举报单号与审核轨迹）。

### P1-3 人审 SLA 与双人复核

- **SLA**：按优先级分档设目标时延（如高危 ≤ 5min），超时告警 + 自动升级；
- **双人复核**：高危类目（涉政/暴恐/儿童）两人独立裁定一致才生效，不一致转第三人；
- **口径一致性**：定期抽检已审样本，统计审核员间一致率（Kappa），发现漂移即复训；
- **埋点**：队列深度、平均等待时长、人均处理量、驳回率。

## 4. P2：数据闭环（让审核自我优化）

### P2-1 流量池动态晋升

**现状**：`poolLevel` 在**发布时**由信用等级一次性决定（`CreditLevel#poolLevel`），此后不变。
后果：优秀内容缺少「跑起来」的上升通道；违规内容只能等举报事后下架。

**方案**：网关只负责**初始池**，后续晋升移到 feed-engine（**跨模块变更**，需与 `docs/modules/tf-feed-engine.md` 的扇出蓝图对齐）：
按滑动窗口内的互动率（完播/点赞/评论/分享）计算晋升/降权，指数退避式放量。

注意：此项**不属于审核模块**，列在此处仅为说明「审核结论与分发联动」的完整链路——
审核的终态（`TAKEN_DOWN`）需能被引擎实时消费并移除内容（当前经 `FeedTimelinePublisher` 同步 HTTP，引擎故障时 fail-open，见 §5 遗留）。

### P2-2 badcase 回流与审核指标

- **回流**：人审结论与机审结论不一致的样本（机审放行但人审驳回 = 漏放；机审拦截但人审放行 = 误杀）
  自动沉淀为 badcase，驱动：词库增补、归一化规则调整、置信度阈值标定、后续模型微调数据；
- **核心指标**：机审拦截占比、人审通过率、漏放率、误杀率、平均审核时长、申诉翻案率；
- **闭环**：指标异常 → 定位到具体规则/词条 → A/B 调整 → 回归验证。

**前置**：P1-1（没有审计表就没有 badcase 数据源）。

## 5. P3：架构级演进

### P3-1 审核独立成服务

**动机**：审核是**计算密集 + 长耗时 + 强独立伸缩需求**的域，与网关（IO 密集、低时延）的资源画像相反。
当前审核跑在网关进程内，会与人审 API、C 端接口争抢同一线程池与连接池。

**方案**（详见 `docs/architecture/service-split.md`）：
- 审核派发与裁定消费抽为独立服务，经 MQ 解耦（复用既有 `MediaEventPublisher` 端口抽象）；
- 网关照旧发布事件，审核服务消费后回写状态；
- **代价**：状态回写引入分布式一致性（需幂等 + 补偿），且失去「同道事务」，属**有明确收益才做**的重构。

### P3-2 视频审核

图片审核是视频审核的基础设施前站。视频需**抽帧 + 音频 ASR + 视觉模型**三路并审，
且单条内容审核成本与时长高一个量级 → 依赖 P0-1 的置信度分级做成本控制（低风险快速放行，
高风险才进重流程）。当前产品形态为纯图片（`max-batch-count=9`），暂无排期。

### P3-3 内容去重

搬运号是 UGC 生态的常见形态。感知哈希（pHash/dHash）+ 最近邻检索可识别重复/轻微改动内容；
结合发布频率与账号年龄，可识别「批量搬运」行为并直接加严。

## 6. 边界与明确不做

- **不做人工审核工具的重前端**：审核台保持在 `turbo-feed-ui/review.html` 的轻量形态，
  不做工单流转 / 权限体系 / 报表看板等运营 SaaS 能力；
- **不引入本地视觉大模型**：本机推理成本与吞吐不匹配上传链路（`AiContentModeration` 保持为接入点桩），
  视觉识别走云内容安全 API（`moderation-mode=cloud`）；
- **审核不阻塞 C 端写入**：所有加严都在「发布后可见性」层，不在上传接口同步等待人审结果。
