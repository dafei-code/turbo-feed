# 架构决策记录（ADR）

> 本目录记录**已经做过、且以后不该被随手推翻**的技术决策。
> 每份 ADR 回答三件事：当时面对什么问题、为什么选这个方案、代价是什么。

## 为什么要有这个目录

代码能告诉你「系统现在怎么做」，但告诉你**为什么不能那样做**。少了后者，接手的人会
在最贵的地方重复交学费：把已经否决过的方案再提一遍、或者顺手改掉一处看起来多余的设计，
而那条设计恰恰是某个故障的唯一防线。

一个具体例子：`tf-shared` 的 `ArchitectureTest` 禁止任何非 JDK 依赖（连 `org.slf4j` 都不行）。
看起来过于严格，直到你要把 traceId 过滤器下沉进去——那时才会发现这条规则逼着你
把「纯逻辑」和「servlet 管道」拆开，而拆开是对的（见 [ADR-0007](0007-observability.md)）。

所以：**写在 ADR 里的代价，就是省下的解释成本。**

## 什么时候必须写一份 ADR

满足任一条就该写（不必是宏大决策）：

1. 选择引入 / 移除一个**第三方依赖或中间件**；
2. 定义或修改**跨服务契约**（字段、版本、语义）；
3. 改动**故障时的行为口径**（fail-open / fail-closed / 降级）；
4. 否决了一个**看起来更简单**的方案（否决理由比选择理由更容易丢）；
5. 做了一处**反直觉**的设计（为了某个约束而绕路）。

## 什么时候不写

- 纯实现细节、可逆的重构、改个变量名——写进 changelog 或 commit message 就够；
- 还没想清楚的探索——先写设计文档，等决策落定再补 ADR。

## 格式

每份 ADR 统一五段（照抄 [0002](0002-nacos-service-discovery.md) 的骨架即可）：

```markdown
# ADR-00NN：一句话标题

- **状态**：提议 / 已采纳（Accepted, YYYY-MM-DD）/ 已废弃 / 被 ADR-00MM 取代
- **所属改进项**：improvement-plan.md §x / Pn-m（没有就写「无」）
- **决策人**：dafei
- **关联 ADR**：…

## 1. 背景（Context）     —— 问题是什么，有哪些约束
## 2. 决策（Decision）     —— 选了什么，逐条写清楚
## 3. 后果（Consequences） —— 正面 + 负面/成本（**必须写负面**，只写优点的 ADR 没有价值）
## 4. 备选方案           —— 否决了什么，为什么（表格）
## 5. 落地记录           —— 实际怎么做的、验证到哪一步、还有什么没做
```

**「负面 / 成本」这一段是硬要求**：一份只列优点的 ADR 等于宣传稿，后来者无法据此判断
是否该推翻它。同样，「落地记录」必须如实区分「已验证」与「待验证」——
本项目多次因为「代码就位但真链路没跑过」而被误认为已完成。

## 状态语义

| 状态 | 含义 | 还能不能照着做 |
|---|---|---|
| 提议（Proposed） | 还没定，正在评估 | 不要据此写代码 |
| 已采纳（Accepted） | 已落地或正在落地 | 可以，但先读「后果」 |
| 已废弃（Deprecated） | 曾经采纳，现在不推荐 | 不要再新增这种用法，存量可留 |
| 被取代（Superseded by ADR-00MM） | 有新决策覆盖了它 | 照新 ADR 做 |

## 修改规则

1. **已采纳的 ADR 不改结论**。想改就写一份新 ADR，在旧的头部的「状态」里标注
   `被 ADR-00MM 取代`——历史结论被悄悄改写的话，这份记录就失去了可信度。
2. **可以追加「落地记录」**（§5）：实际怎么做、验证到哪一步、发现了什么偏差。
   这类补充是增量事实，不是改结论。
3. 新增 ADR 时**必须同时更新本文件的索引表**，否则等于没写。
